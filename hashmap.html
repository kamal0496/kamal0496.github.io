Must-Remember Key Points

  1. HashMap is not thread-safe, allows 1 null key + many null values, and is fastest single-threaded.
  2. ConcurrentHashMap is thread-safe, no null keys/values, using CAS + bucket-level locking (not a whole-map lock).
  3. Java 7: segment locking. Java 8+: segments removed → CAS + synchronized on a bucket + tree bins.
  4. Nulls banned in CHM because get() returning null would be ambiguous (absent vs mapped to null).
  5. get() then put() is a check-then-act race; computeIfAbsent() makes it atomic per key.
  6. Prefer concurrent classes; use synchronized to guard a compound operation across multiple state changes.
  7. HashMap resizes when size > capacity × loadFactor (16 × 0.75 = 12 → resize on the 13th entry); capacity doubles to stay a power of two.
  8. Resize is O(n); normal put/get is O(1) average.

Why no null values in ConcurrentHashMap?

In a concurrent setting you can't tell the two cases apart:

  • Key not present
  • Key present with value null
String value = map.get(key);  // null → absent, or mapped to null?

In a plain HashMap you can follow up with containsKey(), but in a concurrent map another thread could change things between the two calls, so the ambiguity can't be resolved safely.

Short interview answer HashMap is not thread-safe and allows one null key and multiple null values. ConcurrentHashMap is thread-safe, doesn't allow null keys/values, and uses bucket-level locking and CAS operations for better performance in concurrent environments. For multi-threaded backend applications such as caching or session management, ConcurrentHashMap is preferred.

2. ConcurrentHashMap Internals

Before Java 8
  • Map divided into multiple segments
  • Only the segment being modified is locked
Java 8 and above
  • Segments removed
  • CAS operations for updates
  • Synchronization at bucket level when required
  • Red-Black Tree conversion when collisions get high
Added
  • Empty bucket: new node inserted with a lock-free CAS.
  • Non-empty bucket: synchronized on the bucket's head node, so only that bucket is blocked.
  • Reads (get) are generally lock-free (volatile reads).
  • size() is built from a base counter plus striped counter cells, so it's an estimate under concurrent updates.

3. The computeIfAbsent Race

Problem: check-then-act

ConcurrentHashMap<Long, User> cache = new ConcurrentHashMap<>();
User user = cache.get(id);
if (user == null) {
    user = loadUserFromDB(id);
    cache.put(id, user);
}
T1: get(id) → nullT2: get(id) → null→both call loadUserFromDB(id)
Same user loaded twice from the DB → unnecessary work and a performance hit. Each call is atomic, but the sequence isn't.

Fix: atomic compute

User user = cache.computeIfAbsent(id, key -> loadUserFromDB(key));
  1. T1 and T2 both call computeIfAbsent(100)
  2. T1 gets control of that bucket/key and runs the mapping function
  3. Value is inserted
  4. T2 re-checks, finds the value, and returns it
Only one thread runs loadUserFromDB(100).
Added: pitfalls
  • Keep the mapping function short and non-blocking: it holds the bucket while running, blocking other updates to that bucket.
  • Never modify the same map inside the mapping function (can deadlock or throw IllegalStateException: Recursive update).
  • Atomicity is per key; operations spanning multiple keys are not atomic.
  • Related atomic methods: putIfAbsent, computeIfPresent, compute, merge.
  • HashMap.computeIfAbsent exists too but is not thread-safe.
Interview-ready answer computeIfAbsent() prevents the check-then-act race condition. Instead of separately calling get() and put(), it atomically checks whether a key exists and computes the value only when absent. In ConcurrentHashMap, concurrent threads trying to insert the same key coordinate internally so that only one value gets associated with the key, avoiding duplicate object creation and unnecessary database calls. It's commonly used in caches, lazy initialization, and lookup tables.

4. synchronized vs Concurrent Classes

Concurrent classes

Prefer when they solve the problem directly: optimized for scalability, less locking overhead.

  • Thread-safe collections (ConcurrentHashMap)
  • Counters (AtomicInteger)
  • Queues
synchronized

Use to protect a compound business operation with multiple state changes that must execute atomically.

  • Guards critical sections spanning several operations
Added
  • Atomic classes make one variable atomic via CAS. Once an invariant spans multiple variables/collections, you need a lock.
  • Individually atomic calls don't compose: if (!map.containsKey(k)) map.put(k, v) is still a race.
  • Hashtable and Collections.synchronizedMap() lock the whole map on every call, so they scale poorly.
Interview-ready answer I prefer concurrent classes whenever they solve the problem directly because they're optimized for scalability and reduce locking overhead. I use synchronized when I need to protect a compound business operation involving multiple state changes that must execute atomically. Concurrent classes are ideal for thread-safe collections, counters, and queues, while synchronized is suitable for guarding critical sections spanning multiple operations.

5. HashMap Resize & Why Capacity Doubles

threshold = capacity * loadFactor
default: capacity = 16, loadFactor = 0.75
threshold = 16 * 0.75 = 12

Inserting the 13th entry triggers a resize.

Step 1: create new array (2× capacity)→Step 2: rehash / redistribute existing entries
  • Capacity stays a power of two → bucket index via a fast bitwise AND instead of modulo
  • put/get is O(1) average, but resize is O(n) since every entry is relocated
Added: fills in Step 2 
index = (n - 1) & hash     // n = capacity (power of two)
  • When capacity doubles, each entry either stays at the same index or moves to oldIndex + oldCapacity, decided by one extra hash bit (hash & oldCap). No full recomputation needed.
  • Java 8 splits each bucket into a "low" and "high" list and preserves order.
  • Java 7 reversed the order during transfer; concurrent resizes could create a cyclic list → infinite loop. Another reason HashMap must not be shared across threads.
  • HashMap hashes with h ^ (h >>> 16) to spread high bits into the low bits used for the index.
  • Treeification: a bucket becomes a Red-Black tree when its chain reaches 8 nodes and capacity is at least 64 (otherwise it just resizes). It reverts to a list at 6.
  • Pre-size when you know the count: new HashMap<>(expected / 0.75f + 1) avoids repeated resizes. A requested capacity is rounded up to the next power of two.
Interview-ready answer A HashMap resizes when its size exceeds the threshold, which is capacity × loadFactor. During resizing, a new bucket array with double the capacity is created, and existing entries are redistributed. Capacity is always doubled so that it remains a power of two, allowing HashMap to compute bucket indexes efficiently using bitwise operations. Although normal put/get operations are O(1) on average, resizing is an O(n) operation because all existing entries must be relocated.

6. Often-Missed Follow-ups

Added
  • HashMap null key: stored in bucket 0 (hash of null is 0).
  • Mutable keys: changing a key's fields that feed hashCode()/equals() after insertion makes the entry unfindable. Prefer immutable keys.
  • equals/hashCode contract: equal objects must have equal hash codes.
  • Why not Hashtable: legacy, whole-map locking, no nulls.
  • Visibility: CHM guarantees a write happens-before later reads of that key.

Quick Q&A (tap to reveal)

HashMap vs ConcurrentHashMap in one line?

HashMap: not thread-safe, allows nulls, fastest single-threaded. CHM: thread-safe via CAS and bucket-level locking, no nulls, built for concurrent use.

How did CHM change in Java 8?

Segment locking was removed in favour of CAS, bucket-level synchronization, and Red-Black tree bins for heavy collisions.

Why can't CHM store null values?

get() returning null can't distinguish "absent" from "mapped to null", and in a concurrent map you can't safely disambiguate with a second call.

What race does computeIfAbsent solve?

The check-then-act race of get() then put(): it atomically checks and computes, so only one thread loads the value (e.g. one DB call).

When use synchronized over concurrent classes?

For compound operations with multiple state changes that must be atomic together.

When does HashMap resize?

When size exceeds capacity × loadFactor (default 12 for 16 × 0.75), i.e. on the 13th insert.

Why is capacity always a power of two?

Bucket index becomes a cheap bitwise AND, (n-1) & hash, instead of a modulo, and doubling keeps that property.

Cost of resizing?

O(n): all entries are relocated, though put/get are O(1) on average.

Prefer concurrent classes, use computeIfAbsent for atomic caches, and synchronize compound operations.
