Java Executor Framework & ThreadPoolExecutor

Thread pools, Executors, ForkJoinPool, scheduling and Spring TaskExecutor: quick-revision cheat sheet.

Key PointsHierarchyThreadPoolExecutorTask FlowRejectionExecutorsForkJoinScheduledSpringOften MissedQ&A

Must-Remember Key Points

  1. Executor = basic interface, one method execute(Runnable), no return value, no shutdown.
  2. ExecutorService = extends Executor with submit(), invokeAll(), shutdown() etc.
  3. ThreadPoolExecutor = the core implementation; full control over core/max threads, queue, keep-alive, thread factory and rejection policy.
  4. Task flow order: core threads → queue → extra threads up to max → reject. (Queue is used before extra threads.)
  5. corePoolSize = min threads kept alive; maximumPoolSize = hard cap; keepAliveTime = idle time before excess threads die.
  6. Rejection policies: Abort (default), CallerRuns, Discard, DiscardOldest, Custom.
  7. Executors = static factory helpers for pre-configured pools.
  8. ForkJoinPool = work-stealing for recursive divide-and-conquer. ScheduledExecutorService = delayed/periodic tasks.
  9. Spring TaskExecutor = Spring's abstraction, used with @Async.

Added = concept missing from your notes. Correction = something in the notes that is inaccurate; please read these.

1. Executor Hierarchy

Correction

Your diagram showed ForkJoinPool and ScheduledExecutorService as direct "implementations" of ExecutorService. More precisely:

  • ExecutorService extends Executor (interface extends interface).
  • ThreadPoolExecutor and ForkJoinPool both extend AbstractExecutorService.
  • ScheduledExecutorService is an interface extending ExecutorService; ScheduledThreadPoolExecutor extends ThreadPoolExecutor and implements it.

Added: ExecutorService API
  • submit(Runnable | Callable) returns a Future (get(), cancel(), isDone()). Runnable returns nothing and can't throw checked exceptions; Callable returns a value.
  • invokeAll runs a collection and waits for all. invokeAny returns the first successful result.
  • shutdown(): stop accepting new tasks, finish queued ones. shutdownNow(): interrupt running tasks and return the queued ones. awaitTermination() waits for completion.
  • Always shut pools down; non-daemon pool threads keep the JVM alive. Since Java 19, ExecutorService is AutoCloseable.
  • execute vs submit: an exception inside submit() is captured in the Future (silently lost if you never call get()); with execute() it goes to the thread's uncaught exception handler.

2. ThreadPoolExecutor

new ThreadPoolExecutor(
    10,                              // corePoolSize
    20,                              // maximumPoolSize
    60, TimeUnit.SECONDS,            // keepAliveTime
    new LinkedBlockingQueue<>(100),  // workQueue
    threadFactory,                   // how threads are created
    new ThreadPoolExecutor.AbortPolicy() // rejection handler
);
ParameterMeaning
corePoolSizeMinimum threads kept alive, even when idle. Fewer than core running → a new thread is created for each task, even if others are idle.
maximumPoolSizeAbsolute max threads. Extra threads (above core) are only created when the queue is full.
keepAliveTime + unitHow long excess threads (above core) may stay idle before being destroyed.
workQueueHolds tasks waiting for a free thread (see queue types below).
threadFactoryControls thread name, priority, daemon status. Default: Executors.defaultThreadFactory().
handlerRejection policy when queue is full and pool is at max.

Queue types

  • LinkedBlockingQueue(100): FIFO linked list, bounded by the capacity given.
  • ArrayBlockingQueue(50): array-based, bounded.
  • SynchronousQueue: no capacity; direct handoff to a thread. Good for high throughput.
  • Priority queue: tasks run by priority; not recommended (complex).
Correction
  • Worked example is wrong. With core=10, max=20 and a queue of 100, submitting 30 tasks gives 10 threads and 20 queued tasks. Extra threads (11-20) are created only after all 100 queue slots are full. Rejection happens when 20 threads are busy and 100 are queued (task 121 onward, if none finish).
  • The "21st task is rejected" statement only holds if the queue is tiny or zero-capacity (e.g. SynchronousQueue).
  • The priority queue used with a pool must be PriorityBlockingQueue (a BlockingQueue).
  • The handler type is RejectedExecutionHandler (the "RejectionPolicy" in the notes is a conceptual name).
  • The claim that ArrayBlockingQueue is "slightly faster" isn't a reliable rule; choose by boundedness and contention needs.
Added
  • Unbounded queue gotcha: with an unbounded LinkedBlockingQueue, the queue never "fills", so maximumPoolSize is never used and the queue can grow until OutOfMemoryError.
  • allowCoreThreadTimeOut(true) lets core threads time out too. prestartAllCoreThreads() starts them eagerly (by default threads start lazily).
  • Sizing: CPU-bound ≈ number of cores (+1). I/O-bound: more threads, roughly cores × (1 + wait/compute).
  • Monitoring: getPoolSize(), getActiveCount(), getQueue().size(), getCompletedTaskCount(). Name your threads to make thread dumps readable.

3. Task Submission Flow

  1. Threads < corePoolSize? Yes → create a new thread and run the task immediately.
  2. Queue has space? Yes → add to queue and wait for a free thread.
  3. Threads < maximumPoolSize? Yes → create a new thread above core.
  4. Otherwise → run the rejection policy.
Memory hook: Core → Queue → Max → Reject.

4. Rejection Policies

Triggered when the queue is full, all threads are busy and the pool is at maximumPoolSize.

PolicyBehaviour
AbortPolicy (default)Throws RejectedExecutionException
CallerRunsPolicyThe calling thread (e.g. main) runs the task itself
DiscardPolicySilently drops the task, no exception (task is lost)
DiscardOldestPolicyRemoves the oldest queued task, then adds the new one
CustomImplement RejectedExecutionHandler (log, persist, retry...)
Added
  • CallerRuns = back-pressure: the submitter is slowed down because it executes the task itself. A common safe choice for services.
  • Discard policies lose work silently; use only when tasks are truly droppable.
  • Rejection also happens for tasks submitted after shutdown.

5. Executors (Factory Helper)

Definition

Executors = a helper (utility) class with static factory methods that create pre-configured ExecutorServices.

  • It is a class (note the "s"), not the Executor interface.
  • Internally it just builds a ThreadPoolExecutor (or ScheduledThreadPoolExecutor / ForkJoinPool) with preset parameters.
  • Convenient for quick setups, but it hides the queue, max-thread and rejection settings (see table below).
Interview line: Executors is a factory/utility class that gives ready-made thread pools such as fixed, cached, single-thread and scheduled; under the hood they are configured ThreadPoolExecutor instances.

6. ForkJoinPool

Specialized pool for divide-and-conquer (recursive) tasks, using work-stealing.

Split task (fork)→Compute subtasks in parallel→Combine (join)
Added
  • Work-stealing: each worker has its own deque; an idle worker "steals" tasks from the tail of a busy worker's deque, keeping all cores busy.
  • Tasks extend RecursiveTask<V> (returns a value) or RecursiveAction (no result) and implement compute().
  • The common pool (ForkJoinPool.commonPool()) backs parallel streams and the default async CompletableFuture. Avoid blocking I/O there.
  • Best for CPU-bound, divisible work; not for blocking tasks.

7. ScheduledExecutorService

An ExecutorService with scheduling capabilities for delayed and periodic tasks.

Added
  • schedule(task, delay, unit): run once after a delay.
  • scheduleAtFixedRate(task, initialDelay, period, unit): start times are fixed intervals; if a run takes longer than the period, later runs start late (no overlap).
  • scheduleWithFixedDelay(task, initialDelay, delay, unit): waits the delay after each run finishes.
  • If a periodic task throws an exception, later runs are suppressed; catch exceptions inside the task.
  • In Spring, @Scheduled uses a scheduler under the hood.

Correction
  • AsyncTaskExecutor is a loose analogue of ExecutorService (adds submit() returning a Future), not an exact equivalent.
  • In your hierarchy, SimpleAsyncTaskExecutor does not pool: it starts a new thread per task. ThreadPoolTaskExecutor wraps ThreadPoolExecutor; ConcurrentTaskExecutor adapts any existing java.util.concurrent.Executor.
Added: @Async in practice 
@EnableAsync
@Configuration
class AsyncConfig {
  @Bean ThreadPoolTaskExecutor taskExecutor() {
    var e = new ThreadPoolTaskExecutor();
    e.setCorePoolSize(10);
    e.setMaxPoolSize(20);
    e.setQueueCapacity(100);
    e.setThreadNamePrefix("async-");
    e.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    e.initialize();
    return e;
  }
}
@Async CompletableFuture<User> load(long id) { ... }
  • Needs @EnableAsync. @Async methods return void, Future or CompletableFuture.
  • It works through a proxy: calling an @Async method from within the same class (self-invocation) runs synchronously.
  • Without a configured executor, Spring Boot auto-configures a ThreadPoolTaskExecutor (tunable via spring.task.execution.pool.*); plain Spring without Boot may fall back to SimpleAsyncTaskExecutor.
  • Exceptions from void @Async methods need an AsyncUncaughtExceptionHandler.
  • Thread-local context (security, MDC) isn't propagated automatically; use a TaskDecorator.

9. Often-Missed Fundamentals

Added
  • Why thread pools? Reuse threads (creating a thread per task is costly), cap concurrency, queue work, and manage lifecycle in one place.
  • Executor vs Thread: Executor separates task submission from execution policy.
  • Future limitations: get() blocks and there is no chaining; CompletableFuture adds non-blocking composition (thenApply, thenCompose, allOf).
  • Graceful shutdown pattern: shutdown() → awaitTermination(timeout) → if still running, shutdownNow().
  • Thread starvation: tasks that wait on other tasks in the same bounded pool can deadlock it.
  • Separate pools for different workloads (e.g. slow I/O vs fast CPU tasks) so one cannot starve the other.

Quick Q&A (tap to reveal)

Executor vs ExecutorService?

Executor only has execute(Runnable). ExecutorService adds submit() (Futures), invokeAll(), and lifecycle control like shutdown().

Explain the ThreadPoolExecutor task flow.

Fewer than core threads → new thread. Otherwise queue the task. If the queue is full and threads < max → new thread. Otherwise reject.

Difference between corePoolSize and maximumPoolSize?

Core is the minimum kept alive. Max is the hard cap; threads above core are created only when the queue is full and die after keepAliveTime when idle.

Name the rejection policies.

Abort (default, throws), CallerRuns (caller executes), Discard (silently drops), DiscardOldest (drops oldest queued), or a custom handler.

Why avoid Executors.newFixedThreadPool in production?

It uses an unbounded queue, so tasks can pile up until OOM. newCachedThreadPool can create unlimited threads. Prefer a configured ThreadPoolExecutor.

execute() vs submit()?

execute takes a Runnable and returns nothing. submit takes Runnable/Callable and returns a Future that captures results and exceptions.

What is ForkJoinPool good for?

Recursive divide-and-conquer CPU-bound tasks, using work-stealing so idle workers take tasks from busy ones.

scheduleAtFixedRate vs scheduleWithFixedDelay?

Fixed rate starts runs at fixed intervals; fixed delay waits the given delay after each run completes.

How does Spring's @Async use executors?

It runs the method on a TaskExecutor (typically ThreadPoolTaskExecutor) via a proxy; requires @EnableAsync and doesn't work on self-invocation.

Core → Queue → Max → Reject. Use bounded queues, name your threads, and always shut pools down.
