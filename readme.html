Banking Microservices Application

Spring Boot-based banking microservice system simulating a real-world digital banking flow — account management, transaction processing, fraud detection, payment integration, and notifications.

Architecture

Built as an event-driven microservices system:

Spring Boot 3 / Java 17 PostgreSQL Redis (OTP) Apache Kafka Feign clients Razorpay SDK Docker Compose

Services

account-service:8081

Creates accounts, fetches balances, credits/debits, blocks/unblocks accounts, and maintains daily transaction limits.

Data store: PostgreSQL (account_db)
  • GET /api/v1/accounts
  • POST /api/v1/accounts
  • GET /api/v1/accounts/{accountNumber}/balance
  • PUT /api/v1/accounts/{accountNumber}/block · /unblock · /credit · /deduct
transaction-service:8082

Transfers money between accounts, handles transfer-with-payment flow, validates OTPs for suspicious transactions, stores transaction history, and coordinates payment/fraud workflows over Kafka.

Data store: PostgreSQL (transaction_db) + Redis (OTP)
  • POST /api/v1/transactions/transfer
  • POST /api/v1/transactions/transfer-with-payment
  • GET /api/v1/transactions/history/{accountNumber}
  • POST /api/v1/transactions/{transactionId}/verify
payment-service:8084

Creates Razorpay orders, stores payment records, receives Razorpay webhooks, and emits payment.completed / payment.failed events.

Data store: PostgreSQL (payment_db)
  • POST /api/v1/payments/create-order
  • POST /api/v1/payments/webhook
fraud-detection-service:8083

Listens for transaction-initiation events, checks sender balance to judge risk, and triggers a verification flow for suspicious transactions.

Consumes: transaction.initiated  ·  Produces: verification.required, fraud.check.clean
notification-service:8085

Consumes event notifications from Kafka and logs alerts for OTP generation, transaction status, refunds, fraud alerts, and payment results. Currently logs to console rather than sending real emails/SMS.

Consumes: transaction.otp.generated, transaction.completed, fraud.detected, transaction.refunded, payment.completed, payment.failed
api-gateway:9090

Central entry point for client-facing requests, routing to account-service, transaction-service, and payment-service.

Application Workflow

Standard bank transfer

  1. Client calls POST /api/v1/transactions/transfer via the gateway or directly.
  2. transaction-service deducts the sender's balance via a Feign call to account-service.
  3. A transaction record is created with status PROCESSING, and a transaction.initiated event is published to Kafka.
  4. fraud-detection-service evaluates the transaction and emits either fraud.check.clean or verification.required.
  5. If suspicious: transaction-service generates a 6-digit OTP, stores it in Redis with a 5-minute expiry, and emits transaction.otp.generated — notification-service logs/alerts the user.
  6. Client verifies via POST /api/v1/transactions/{transactionId}/verify?otp=XXXXXX.
  7. If valid: transaction is marked COMPLETED, the receiver is credited, and notification-service confirms it.
  8. If invalid or expired: the transaction fails, the sender's account is blocked/flagged, a refund is triggered, and fraud.detected / transaction.refunded events are emitted.

Transfer with Razorpay payment

  1. Client calls POST /api/v1/transactions/transfer-with-payment.
  2. transaction-service creates the transaction in PAYMENT_PENDING state and requests a payment order from payment-service.
  3. payment-service creates a Razorpay order and returns order ID + key details to the frontend.
  4. The frontend completes payment; Razorpay sends a webhook to POST /api/v1/payments/webhook.
  5. payment-service validates the event, updates the payment record, and publishes payment.completed or payment.failed.
  6. transaction-service consumes the event and either completes the transfer or fails it and triggers a refund.
  7. notification-service logs the outcome.
Each service owns its own database, async events decouple the services, Redis handles short-lived OTP checks, and Kafka provides reliable event-driven coordination between them.

Running it locally

Requires Docker and Docker Compose (or Java 17+, PostgreSQL, and Redis if running services directly).

# from the project root
docker-compose up -d

Example requests

Create a new account

curl -X POST http://localhost:8081/api/v1/accounts \
  -H "Content-Type: application/json" \
  -d '{
    "accountHolderName": "John Doe",
    "email": "john@example.com",
    "phone": "9876543210",
    "initialDeposit": 10000,
    "accountType": "SAVING"
  }'

Transfer money

curl -X POST http://localhost:8082/api/v1/transactions/transfer \
  -H "Content-Type: application/json" \
  -d '{
    "senderAccountNumber": "123456789012",
    "receiverAccountNumber": "987654321098",
    "amount": 1000,
    "description": "Wallet transfer",
    "currency": "INR"
  }'

Verify OTP

curl -X POST "http://localhost:8082/api/v1/transactions/{transactionId}/verify?otp=123456"

Notes & caveats

  • This is a demo/learning application — some notification logic is simulated via logs rather than real email/SMS.
  • Fraud detection currently uses a simplified random-risk decision, intended as a sample implementation.
  • Sensitive credentials are managed through .env and should never be committed to a public repository.
  • The API gateway may need additional routing/security hardening for production use.
