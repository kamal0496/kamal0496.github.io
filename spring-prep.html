1@Transactional readOnly = true vs false

DefinitionreadOnly is a hint on @Transactional declaring that the method only reads data. false (default) allows reads and writes; true lets Spring/Hibernate/the database apply read-only optimisations.
  • readOnly=false (default): full transaction (begin/commit/rollback), Hibernate dirty checking on, flush mode AUTO (changes flushed before queries/commit).
  • readOnly=true: Hibernate skips dirty checking, flush mode MANUAL (no auto flush), DB/driver may optimise or route to read replicas; writes may throw depending on the DB/driver.
  • Best practice: use readOnly = true for query methods. It signals intent and saves work. It is not a security feature.
@Service
@Transactional(readOnly = true)              // class-level default for queries
public class OrderService {
    public List<Order> findAll() { return repo.findAll(); }

    @Transactional                            // method-level override → read-write
    public Order place(Order o) { return repo.save(o); }
}
Corrections
  • "readOnly=false acquires write locks" is imprecise. A read-write transaction doesn't lock anything by existing; row locks are taken when you actually update/delete (or use SELECT ... FOR UPDATE).
  • With Hibernate, writes in a readOnly transaction are usually silently not flushed (no exception) unless the DB enforces read-only (e.g. PostgreSQL does).
Added
  • Spring also calls connection.setReadOnly(true) and Hibernate sets the session read-only: loaded entities aren't snapshotted, saving memory.
  • Joining a transaction: if a readOnly method is called inside an existing read-write transaction (REQUIRED), the outer settings win; readOnly is only honoured when the transaction starts there.
  • Typical use: route reads to replicas via a routing DataSource keyed on TransactionSynchronizationManager.isCurrentTransactionReadOnly().
Follow-up Does readOnly=true prevent repo.save() from writing?
Not reliably. Hibernate won't flush, but a driver/DB with read-only enforcement may throw. Never rely on it for protection.
Follow-up Why is it faster?
No dirty-check pass over every loaded entity at flush time, no snapshot copies, no flush; the DB may use cheaper snapshots/locks.
Follow-up A readOnly method calls a read-write method on another bean. What happens?
With REQUIRED the inner method joins the outer (read-only) transaction, so its writes may not be flushed. Use REQUIRES_NEW or restructure.

2Types of Dependency Injection

DefinitionDependency Injection (DI) means the Spring container supplies an object's dependencies instead of the object creating them. Spring supports three styles: constructor, setter and field injection.
  • Constructor (recommended): dependencies can be final (immutability), easy unit testing, all dependencies present at construction, explicit contract.
  • Setter: for optional dependencies or reconfiguration; object can be partially constructed.
  • Field (avoid): hard to test (needs reflection/Spring), no final, hidden dependencies; only for prototypes/legacy.
@Service
public class OrderService {
    private final PaymentClient payment;                    // final → immutable
    public OrderService(PaymentClient payment) {            // @Autowired optional with ONE constructor
        this.payment = payment;
    }
}
// Lombok: @RequiredArgsConstructor generates the constructor for final fields
Correction Constructor injection doesn't prevent circular dependencies "at compile time". It fails fast at application startup (BeanCurrentlyInCreationException). Since Spring Boot 2.6, circular references are prohibited by default (spring.main.allow-circular-references).
Added
  • Choosing among several beans of one type: @Primary (default choice) or @Qualifier("name"). Resolution is by type, then by name.
  • Errors: NoSuchBeanDefinitionException (none found), NoUniqueBeanDefinitionException (several, no tie-break).
  • Inject all implementations: List<PaymentStrategy> or Map<String, PaymentStrategy> (bean name → bean).
  • Optional dependency: Optional<X>, @Autowired(required=false) or ObjectProvider<X>.
Follow-up A depends on B and B on A. How do you fix it?
Redesign (extract a third bean or use events); as workarounds, setter injection or @Lazy on one dependency.
Follow-up Why is field injection hard to test?
You can't pass mocks through a constructor; you need reflection (@InjectMocks/ReflectionTestUtils) or a Spring context.
Follow-up Two beans implement the same interface. How does Spring pick one?
@Primary wins; otherwise @Qualifier; otherwise matching the parameter/field name to the bean name; otherwise it throws.

3Spring Boot Auto-Configuration

DefinitionAuto-configuration automatically registers Spring beans for you, based on what is on the classpath, which beans you've already defined, and which properties you've set. You override it simply by defining your own beans.
@SpringBootApplication→@EnableAutoConfiguration→AutoConfigurationImportSelector→Candidate config classes→@Conditional checks→Matching ones applied
  • Each auto-config class is guarded by conditions, e.g. HikariCP on classpath → configure it; your own DataSource bean exists → skip; spring.datasource.url set → use it.
  • User configuration always takes precedence. Convention over configuration: opinionated but customisable.
  • Debug: debug=true (or --debug) prints the conditions report. Exclude: @SpringBootApplication(exclude=...).
Correction Candidates are no longer read from META-INF/spring.factories in modern Boot. Spring Boot 2.7 introduced META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports, and Boot 3 uses only that file for auto-configuration (spring.factories remains for other extension points).
Added 
@AutoConfiguration
@ConditionalOnClass(DataSource.class)
public class MyAutoConfig {
    @Bean
    @ConditionalOnMissingBean                       // back off if user defines their own
    public MyService myService() { return new MyService(); }
}
// listed in META-INF/spring/...AutoConfiguration.imports
  • @SpringBootApplication = @SpringBootConfiguration + @EnableAutoConfiguration + @ComponentScan.
  • Common conditions: @ConditionalOnClass, @ConditionalOnMissingBean, @ConditionalOnProperty, @ConditionalOnWebApplication.
  • Exclude also via spring.autoconfigure.exclude. Starters bring the dependencies that trigger the conditions.
Follow-up How would you create your own starter?
Write an auto-configuration class with conditions, register it in the .imports file, and publish it with a starter module (+ optional @ConfigurationProperties).
Follow-up An auto-configured bean isn't what you want. Options?
Define your own bean (auto-config backs off via @ConditionalOnMissingBean), set properties, or exclude the auto-config class.
Follow-up How do you find out why something was (not) configured?
Run with --debug and read the "Positive matches / Negative matches" report, or use the Actuator conditions endpoint.

4@Transactional Propagation

DefinitionPropagation defines how a transactional method behaves when it is called while a transaction is already active: join it, start a new one, suspend it, or refuse to run.
TypeBehaviourTypical use
REQUIRED (default)Join existing, else create newNormal service methods
REQUIRES_NEWAlways new; suspends the outer oneAudit logging that must commit even if the caller rolls back
SUPPORTSJoin if exists, else run non-transactionallyOptional-read helpers
NOT_SUPPORTEDRun without a transaction (suspends existing)Long non-DB work
MANDATORYMust have one, else exceptionMethods that must never run standalone
NEVERMust NOT have one, else exceptionGuarding non-transactional code
NESTEDSavepoint inside the outer transactionPartial rollback of a sub-step
Added 
@Transactional
public void placeOrder(Order o) {
    orderRepo.save(o);
    auditService.log(o);          // REQUIRES_NEW: commits independently
}
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void log(Order o) { auditRepo.save(new Audit(o)); }
  • Rollback rules: by default only RuntimeException and Error roll back; checked exceptions don't. Use rollbackFor = Exception.class.
  • Proxy limits: works through a Spring proxy, so self-invocation (this.method()) bypasses it; use public methods on Spring beans (not private/final).
  • REQUIRES_NEW uses a second DB connection: risk of pool exhaustion/deadlock under load.
  • NESTED needs savepoint support (JDBC DataSourceTransactionManager); JpaTransactionManager support is limited.
  • If an inner REQUIRED method throws a runtime exception, the shared transaction is marked rollback-only; the outer commit then fails with UnexpectedRollbackException.
Follow-up Your @Transactional method calls another method of the same class with REQUIRES_NEW. What happens?
Nothing new starts: self-invocation bypasses the proxy, so the call runs in the same transaction. Move it to another bean.
Follow-up A checked exception is thrown. Is the transaction rolled back?
No, it commits by default. Add rollbackFor.
Follow-up REQUIRES_NEW vs NESTED?
REQUIRES_NEW is a fully independent transaction (own connection, commits separately). NESTED is part of the outer transaction using a savepoint; if the outer rolls back, so does the nested one.

5Bulkhead Pattern

DefinitionThe Bulkhead pattern isolates resources (threads, connections, concurrency slots) into separate compartments so a failure or slowdown in one area can't exhaust shared resources and cascade to others, like watertight compartments on a ship.

Without: all requests share one pool; one slow downstream hogs the threads and everything fails. With: each dependency gets its own limited compartment (e.g. 5 threads for Service A, 5 for Service B).

SEMAPHORE (default)THREADPOOL
Runs inCaller's threadSeparate dedicated threads
LimitsConcurrent calls via permitsPool size + queue
OverheadLowHigher (context switches)
IsolationLimits concurrency, doesn't isolate threadsTrue thread isolation
 
resilience4j.bulkhead.instances.semaphoreBulkhead.max-concurrent-calls=10
resilience4j.bulkhead.instances.semaphoreBulkhead.max-wait-duration=5s

resilience4j.thread-pool-bulkhead.instances.threadpoolBulkhead.core-thread-pool-size=5
resilience4j.thread-pool-bulkhead.instances.threadpoolBulkhead.max-thread-pool-size=10
resilience4j.thread-pool-bulkhead.instances.threadpoolBulkhead.queue-capacity=100
  • Rejected calls throw BulkheadFullException. Use for external calls, expensive operations, differing priorities; combine with Circuit Breaker.
Corrections
  • A THREADPOOL bulkhead method must return CompletableFuture<T> (it runs asynchronously). Your example returning User works only for SEMAPHORE.
  • "THREADPOOL is recommended" is context-dependent: it adds overhead and loses ThreadLocal context (security, MDC). SEMAPHORE is often enough, especially with virtual threads.
Added 
@Bulkhead(name = "semaphoreBulkhead", fallbackMethod = "fallback")
public User getUser(Long id) { return client.fetch(id); }

@Bulkhead(name = "threadpoolBulkhead", type = Bulkhead.Type.THREADPOOL)
public CompletableFuture<User> getUserAsync(Long id) {
    return CompletableFuture.completedFuture(client.fetch(id));   // runs in the bulkhead's pool
}
User fallback(Long id, BulkheadFullException e) { return User.guest(); }
  • Other Resilience4j patterns: CircuitBreaker (CLOSED → OPEN → HALF_OPEN), Retry, RateLimiter, TimeLimiter. Default aspect order: Retry → CircuitBreaker → RateLimiter → TimeLimiter → Bulkhead.
  • Bulkhead protects capacity; Circuit Breaker stops calling a failing service; they complement each other.
  • You can also bulkhead with separate connection pools or Tomcat/executor pools per workload.
Follow-up Bulkhead vs Circuit Breaker vs Rate Limiter?
Bulkhead: caps concurrent usage of a resource. Circuit Breaker: stops calls after failure threshold, then probes. Rate Limiter: caps calls per time period.
Follow-up What happens when the bulkhead is full?
The call waits up to max-wait-duration (semaphore) or queues (thread pool); then BulkheadFullException, handled by a fallback.

6When Do Singleton Beans Cause Issues?

DefinitionSpring's default singleton scope creates one bean instance per container (per bean definition) and shares it across all threads. It is not automatically thread-safe.
  • Problems arise with mutable shared state: counters, request-specific data, collections, caches without synchronisation, leading to race conditions and corruption.
  • Fix: keep beans stateless, use method-local variables for request data, and thread-safe structures (ConcurrentHashMap, AtomicInteger) when shared state is unavoidable.
@Service class Bad  { private int count;                              void hit(){ count++; } }   // race
@Service class Good { private final AtomicInteger count = new AtomicInteger(); void hit(){ count.incrementAndGet(); } }
Added 
@Component class Single {
    @Autowired ObjectProvider<Proto> provider;   // prototype injected once otherwise!
    void run(){ Proto p = provider.getObject(); }   // alternatives: @Lookup, @Scope(proxyMode = TARGET_CLASS)
}
  • Spring singleton ≠ GoF singleton: one per container, not per JVM.
  • Typical bugs: current user stored in a field, shared SimpleDateFormat, mutable HashMap caches.
  • A stateless singleton with thread-safe dependencies is itself thread-safe.
Follow-up Prototype bean injected into a singleton: how many instances?
One, created at injection time. Use ObjectProvider, @Lookup or a scoped proxy.
Follow-up How do you handle per-request data safely?
Method parameters/locals or request-scoped beans (via proxy); never fields on singletons.

7Connection Pooling

DefinitionA connection pool keeps a set of open, reusable database connections that requests borrow and return, avoiding the cost of opening a new connection (TCP + authentication) for every request.
Init min connections→Borrow→Execute query→Return to pool
  • Idle timeout: idle connections are closed. Max size: grows up to max when all are busy. Validation: dead connections are removed.
Added: HikariCP (Spring Boot default) 
spring.datasource.hikari.maximum-pool-size=10      # default 10
spring.datasource.hikari.minimum-idle=10           # default = max
spring.datasource.hikari.connection-timeout=30000  # wait for a free connection
spring.datasource.hikari.idle-timeout=600000       # trims idle conns above minimum-idle
spring.datasource.hikari.max-lifetime=1800000      # retire before DB/firewall drops it
spring.datasource.hikari.leak-detection-threshold=20000   # off by default
  • close() on a pooled connection returns it to the pool; it doesn't close the socket.
  • Exhausted pool: threads wait connection-timeout, then SQLTransientConnectionException. Causes: leaks, long transactions, slow queries, remote calls inside @Transactional, spring.jpa.open-in-view=true (default).
  • Sizing: bigger isn't faster; start small (≈ cores × 2 + spindles). Total across instances must stay under DB max_connections.
Follow-up 200 Tomcat threads, pool of 10. What happens under load?
Up to 190 threads wait for a connection and may time out. Shorten transactions/queries rather than blindly raising the pool.
Follow-up Why does REQUIRES_NEW risk pool exhaustion?
The suspended outer transaction keeps its connection while the inner takes a second one; many concurrent requests can deadlock the pool.

8Filter vs Interceptor

DefinitionA Filter is a Servlet-spec component that intercepts requests/responses before they reach Spring's DispatcherServlet. An Interceptor is a Spring MVC component that runs around the controller, after the DispatcherServlet has chosen a handler.
FilterInterceptor
Belongs toServlet specificationSpring MVC
Methodsinit(), doFilter(), destroy()preHandle(), postHandle(), afterCompletion()
Wrap request/responseYesNo (modify only)
Spring contextLimitedFull access
Knows handler methodNoYes
Use forCORS, encoding, compression, security headers, token validation, raw loggingRole-based authorization, per-endpoint metrics, model/view work
Added
Filter chain→DispatcherServlet→preHandle→Controller→postHandle→afterCompletion→Filter (after)
@Component
class TimingFilter extends OncePerRequestFilter {
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        long t = System.nanoTime();
        chain.doFilter(req, res);                // forget this → request never proceeds
        log.info("{} took {}ms", req.getRequestURI(), (System.nanoTime() - t) / 1_000_000);
    }
}
@Configuration class WebConfig implements WebMvcConfigurer {
    public void addInterceptors(InterceptorRegistry r) { r.addInterceptor(new AuthInterceptor()).addPathPatterns("/api/**"); }
}
  • preHandle returns boolean (false stops the chain). postHandle is skipped if the handler throws; afterCompletion always runs (if preHandle returned true).
  • Spring Security is a filter chain. Exceptions in filters don't reach @ControllerAdvice.
  • The request body can be read once; wrap with ContentCachingRequestWrapper to log it.
Follow-up Where do you validate a JWT?
In a filter (Spring Security chain) so unauthenticated requests are rejected before MVC; fine-grained authorization can use interceptors or method security.
Follow-up Filter vs Interceptor vs AOP?
Filter: servlet request level. Interceptor: MVC handler level. AOP: any Spring bean method, independent of HTTP.

10Spring Boot vs Spring Framework

DefinitionSpring Framework is the core platform (IoC, DI, AOP, MVC, Data, Security...). Spring Boot is an opinionated layer on top of it that removes boilerplate configuration and makes apps runnable out of the box. It is not a replacement.

Plain Spring pain: manual XML/Java config (DispatcherServlet, pool, transaction manager), manual dependency version compatibility, deploying to an external Tomcat.

Boot mechanismWhat it gives
Auto-ConfigurationBeans configured from classpath/properties
Starter dependenciesOne dependency pulls a compatible set (e.g. spring-boot-starter-web)
Embedded serverTomcat/Jetty/Undertow inside an executable JAR
Production-ready featuresActuator: health, metrics, info
 
@SpringBootApplication
public class App { public static void main(String[] a) { SpringApplication.run(App.class, a); } }
Added
  • Dependency management: Boot's parent/BOM pins compatible versions.
  • Externalised configuration: application.yml, profiles (application-prod.yml), env vars, command-line args.
  • Executable "fat" JAR (java -jar), DevTools, Docker/native image support.
Follow-up Can you use Spring without Boot? Boot without Tomcat?
Yes to both: Spring alone with manual config; Boot with Jetty/Undertow, or as a non-web app (spring.main.web-application-type=none).
Follow-up Order of property precedence in Boot?
Roughly: command-line args > system properties/env vars > profile-specific config files > application.yml > defaults.

11Microservices Architecture

DefinitionMicroservices is an architectural style where an application is a collection of small, independent, loosely coupled services, each owning one business capability, its own codebase and its own database, communicating over the network (REST, gRPC, or messaging like Kafka/RabbitMQ).
  • Why: independent deployability, independent scalability, technology heterogeneity, fault isolation, easier to understand and maintain at scale.
  • Honest trade-offs: network latency and partial failures; distributed data consistency; need for service discovery, API gateway, tracing, centralised logging; harder integration testing.
Added: patterns you should name
ConcernPattern / tool
Entry pointAPI Gateway
Locating servicesService discovery (Eureka, Consul, Kubernetes DNS)
Data consistencyDatabase per service, Saga, outbox, eventual consistency
ResilienceCircuit breaker, retry, timeout, bulkhead (Resilience4j)
ConfigConfig server / Kubernetes ConfigMaps
ObservabilityDistributed tracing (trace IDs), centralised logs, metrics
CommunicationSynchronous (REST/gRPC) vs asynchronous (events)
  • Idempotency: retries and at-least-once delivery mean handlers must tolerate duplicates.
  • When NOT to use: small teams/simple domains; a modular monolith is often the better start.
Follow-up How do you keep data consistent across services?
No distributed ACID transaction; use the Saga pattern (choreography or orchestration with compensating actions), outbox pattern for reliable events, and accept eventual consistency.
Follow-up A downstream service is slow. What protects you?
Timeouts, circuit breaker, bulkhead, retries with backoff, fallbacks, and async messaging where possible.
Follow-up How do you decide service boundaries?
By business capability / bounded context (domain-driven design), not by technical layers; each service should change and deploy independently.

12API Gateway

DefinitionAn API Gateway is a single entry point between clients and the microservices. All external requests hit it first; it routes them to the right downstream service(s) and handles cross-cutting concerns.

Problems it solves: clients would need every service's address (tight coupling), auth/rate-limiting/logging would be duplicated in each service, and a screen needing data from 3 services would need 3 round trips.

  • Responsibilities: routing, authentication & authorization, rate limiting/throttling, request aggregation, cross-cutting concerns (logging, trace-ID propagation, CORS, response transformation), load balancing.
Added: Spring Cloud Gateway 
spring:
  cloud:
    gateway:
      routes:
        - id: order-service
          uri: lb://order-service            # load-balanced via service discovery
          predicates: [ Path=/api/orders/** ]
          filters:    [ StripPrefix=1 ]
  • Core concepts: Route, Predicate (match request), Filter (modify). It's reactive (WebFlux/Netty). Zuul 1 is retired.
  • Keep business logic out of the gateway. Avoid a single point of failure by running multiple gateway instances behind a load balancer.
  • Gateway vs load balancer: an LB spreads traffic across identical instances; a gateway understands APIs (routing by path, auth, aggregation). BFF = a gateway tailored per client type.
Follow-up Is the gateway a single point of failure? How do you mitigate it?
Run it as a scaled, stateless cluster behind a load balancer, with health checks and rate limits.
Follow-up Where do authentication and authorization belong?
Authenticate (validate the token) at the gateway; each service still enforces its own authorization (zero trust).

13Thread Starvation

DefinitionThread starvation is when a thread is able to run but is repeatedly denied a resource (CPU time, a lock, a thread-pool slot) because other threads keep being favoured. It isn't deadlocked; it just keeps losing.
  • Causes: unfair lock scheduling, high-priority threads dominating CPU, thread-pool exhaustion / bad task design, greedy synchronized blocks, read-write lock imbalance.
  • Mitigation: fair locks (new ReentrantLock(true)), short critical sections (no I/O while holding a lock), don't tweak thread priorities, check for fairness mode on read-write locks.
Added 
ExecutorService pool = Executors.newFixedThreadPool(1);
pool.submit(() -> pool.submit(() -> "inner").get());   // outer holds the only thread waiting for inner → hangs
ProblemWhat happens
DeadlockThreads wait on each other in a cycle; no progress ever
LivelockThreads keep reacting to each other and change state, but make no progress
StarvationOne thread can progress in theory but never gets its turn
  • In Spring apps: a small shared pool (e.g. @Async, Tomcat, a single executor) filled with slow/blocking tasks starves others. Use separate pools per workload (bulkhead idea).
Follow-up Starvation vs deadlock?
Deadlock: a cycle of waiting, permanent. Starvation: no cycle; the thread is just perpetually deprioritised and may recover if contention drops.
Follow-up How would you detect it in production?
Thread dumps (jstack), pool metrics (active/queue size, rejected), lock contention profiling, and latency percentiles for specific request types.

14Spring Bean Lifecycle

DefinitionThe bean lifecycle is the sequence of steps the container performs for a bean, from creation and dependency injection, through initialisation callbacks, to use and finally destruction when the context closes.
1 Instantiate→2 Inject properties→3 Aware callbacks→4 BPP before-init→5 @PostConstruct→6 afterPropertiesSet→7 custom init-method→8 BPP after-init→Ready
Shutdown:@PreDestroy→DisposableBean.destroy→custom destroy-method
  • Aware: BeanNameAware, BeanFactoryAware, ApplicationContextAware. BeanPostProcessors apply to all beans.
  • Prefer @PostConstruct/@PreDestroy over implementing interfaces. Prototype beans: Spring doesn't call destroy callbacks. Singletons are destroyed when the context closes.
Correction (order) Your list puts @PostConstruct together with the custom init method after afterPropertiesSet. Actual order: @PostConstruct → afterPropertiesSet() → @Bean(initMethod). On destroy: @PreDestroy → destroy() → destroyMethod.
Added 
@Component
class CacheLoader {
    private final Repo repo;
    CacheLoader(Repo repo) { this.repo = repo; }      // 1-2: instantiate + inject
    @PostConstruct void warmUp() { /* dependencies are ready here */ }
    @PreDestroy   void close()   { /* release resources */ }
}
  • AOP proxies are created in postProcessAfterInitialization, so @PostConstruct runs on the raw target (before the proxy); @Transactional isn't active inside it.
  • The constructor runs before injection of field/setter dependencies, so don't use them there.
  • Use ApplicationReadyEvent/CommandLineRunner for startup work needing a fully started app.
Follow-up Can you use @Transactional in @PostConstruct?
No, the proxy doesn't exist yet. Run it after startup (e.g. ApplicationReadyEvent listener) or call through another bean.
Follow-up What is a BeanPostProcessor used for?
Hooks into every bean's creation: AOP proxies, @Autowired processing, @PostConstruct handling, custom wrapping.

15Spring Data JPA Query Types

DefinitionSpring Data JPA lets you query through repository interfaces. Besides built-in CRUD, it supports several ways to define queries, from method names to dynamic Specifications.
interface UserRepo extends JpaRepository<User, Long>, JpaSpecificationExecutor<User> {
    List<User> findByStatusAndAgeGreaterThan(String status, int age);            // derived

    @Query("select u from User u where u.email = :email")                      // JPQL
    Optional<User> byEmail(@Param("email") String email);

    @Query(value = "select * from users where created > now() - interval '7 day'", nativeQuery = true)
    List<User> recent();                                                        // native

    @Modifying @Transactional
    @Query("update User u set u.status = :s where u.id = :id")                 // update/delete
    int updateStatus(@Param("id") Long id, @Param("s") String s);

    Page<User> findByStatus(String status, Pageable pageable);                   // paging
    interface Summary { String getName(); String getEmail(); }                  // interface projection
    List<Summary> findByStatus(String status);
}
  • Derived queries: generated from method names. @Query: JPQL (database-agnostic) with @Param. Native: DB-specific, less portable. @Modifying: UPDATE/DELETE, needs a transaction. Named queries: @NamedQuery on the entity. Projections: fetch only needed fields (interface/DTO/record). Specifications: dynamic conditional queries. Pageable/Page<T>: paging and sorting.
Nuance Derived queries are validated at startup but aren't compile-time type-safe (they're method-name strings). Type safety comes from the JPA metamodel/QueryDSL.
Added
  • N+1 problem: 1 query for the parents + N lazy queries for children. Fix with JOIN FETCH, @EntityGraph, or batch fetching. 
    @Query("select o from Order o join fetch o.items where o.id = :id")
Optional<Order> withItems(@Param("id") Long id);
  • @Modifying(clearAutomatically = true) avoids stale persistence-context entities after a bulk update.
  • Lazy loading: accessing a lazy association outside a session → LazyInitializationException. Prefer DTO projections or fetch joins over open-in-view.
  • findById hits the DB; getReferenceById returns a lazy proxy. JpaRepository extends PagingAndSortingRepository → CrudRepository.
Follow-up How do you spot and fix N+1?
Enable SQL logging/Hibernate statistics, notice repeated selects, then use fetch join/@EntityGraph/batch size or a projection.
Follow-up Pagination on a join-fetch collection?
Hibernate pages in memory (warning HHH90003004); paginate the parent IDs first, then fetch the children.
Follow-up When choose native over JPQL?
For DB-specific features, complex reports or performance hints; accept reduced portability.

16ACID

DefinitionACID is the set of four properties that make database transactions reliable: Atomicity, Consistency, Isolation, Durability.
  • Atomicity: all or nothing; no partial completion.
  • Consistency: moves the DB from one valid state to another; constraints/rules are enforced.
  • Isolation: concurrent transactions don't see each other's intermediate states.
  • Durability: committed changes survive crashes (write-ahead logging).

Example: a bank transfer debits one account and credits another atomically, never leaves a negative balance, is isolated from concurrent transfers, and is permanent after commit.

Added: isolation levels vs anomalies (SQL standard)

@Transactional(isolation = Isolation.REPEATABLE_READ)
public void transfer(long from, long to, BigDecimal amt) { /* debit + credit */ }
  • *Some engines (InnoDB, PostgreSQL) prevent phantoms at REPEATABLE_READ via gap locks/snapshots.
  • Dirty read: reading uncommitted data. Non-repeatable read: same row read twice gives different values. Phantom: same query returns different rows.
  • Higher isolation = fewer anomalies but more locking/contention.
  • @Transactional gives ACID only within one database transaction. Across microservices use Saga (BASE/eventual consistency) or 2PC.
Nuance "READ COMMITTED is the default in most databases" is true for PostgreSQL, Oracle and SQL Server, but MySQL InnoDB defaults to REPEATABLE READ. Spring's Isolation.DEFAULT uses the database's own default.
Follow-up Which anomalies does READ_COMMITTED allow?
Non-repeatable reads and phantom reads (not dirty reads).
Follow-up How is durability implemented?
Changes are written to a write-ahead/redo log and flushed to disk at commit before acknowledging; the DB replays it after a crash.
Follow-up How do you get "ACID" across two microservices?
You don't get a single ACID transaction; use Saga with compensating actions (eventual consistency) or, rarely, two-phase commit.

IoC, Beans & Configuration

IoC vs DI?
IoC is the principle: the framework controls object creation and lifecycle. DI is the mechanism: it injects the dependencies.
@Component vs @Service vs @Repository vs @Controller?
All are stereotypes registered by component scan. @Service/@Controller add semantics; @Repository also enables persistence exception translation to Spring's DataAccessException.
@Bean vs @Component?
@Component marks your own class for scanning. @Bean is a factory method in a @Configuration class, used for third-party classes or custom construction logic.
Bean scopes?
singleton (default), prototype, and web scopes request, session, application (+ websocket). Use a scoped proxy when injecting a shorter-lived scope into a singleton.
What does @Configuration do differently from @Component?
Its class is CGLIB-proxied, so calling one @Bean method from another returns the same singleton (not a new instance each call).
@Value vs @ConfigurationProperties?
@Value("${x}") injects single values (supports SpEL). @ConfigurationProperties binds a group into a typed class, with relaxed binding and validation; preferred for structured config.
How do Spring Profiles work?
Activate with spring.profiles.active; @Profile("dev") beans and application-dev.yml load only for that profile.

AOP

What is AOP? Name the terms.
It modularises cross-cutting concerns (logging, transactions, security). Aspect: the module; Advice: the action (@Before, @After, @Around...); Pointcut: which methods; Join point: a method execution. 
@Aspect @Component
class TimingAspect {
    @Around("execution(* com.app.service..*(..))")
    Object time(ProceedingJoinPoint pjp) throws Throwable {
        long t = System.nanoTime();
        try { return pjp.proceed(); } finally { log.info("{} took {}ns", pjp.getSignature(), System.nanoTime() - t); }
    }
}
JDK dynamic proxy vs CGLIB? Why does self-invocation skip AOP?
JDK proxies work on interfaces; CGLIB subclasses the class (Boot default). Advice is applied by the proxy wrapper; an internal this.method() call bypasses the proxy, so @Transactional, @Async, @Cacheable don't apply. Call through another bean or inject self.

MVC & REST

Request flow through Spring MVC?
Filters → DispatcherServlet → HandlerMapping → interceptors → controller → HttpMessageConverter (JSON) / ViewResolver → response.
@Controller vs @RestController? @PathVariable vs @RequestParam vs @RequestBody?
@RestController = @Controller + @ResponseBody. @PathVariable: /users/{id}; @RequestParam: ?page=1; @RequestBody: JSON body mapped to an object.
How do you handle exceptions globally?
@RestControllerAdvice
class GlobalHandler {
    @ExceptionHandler(NotFoundException.class)
    ResponseEntity<ApiError> notFound(NotFoundException e) { return ResponseEntity.status(404).body(new ApiError(e.getMessage())); }
}
Also ResponseStatusException, and validation via @Valid (failures raise MethodArgumentNotValidException → 400).
PUT vs PATCH vs POST? What is idempotency?
PUT replaces a resource (idempotent), PATCH partially updates, POST creates (not idempotent). Idempotent = repeating the call has the same effect as once; vital for retries.

Security

Authentication vs authorization? Typical JWT flow?
Authentication: who are you. Authorization: what may you do. JWT flow: login → server issues signed token → client sends Authorization: Bearer ... → a filter validates signature/expiry and populates the SecurityContext → authorization via roles (@PreAuthorize). Store passwords hashed with BCrypt.
What is CSRF and do stateless JWT APIs need it?
CSRF tricks a browser into sending authenticated requests using cookies. Stateless APIs using bearer tokens in headers (not cookies) can usually disable it; cookie-based sessions need it.

JPA & Data

Entity lifecycle states? What is the persistence context?
Transient → Managed (persistent) → Detached → Removed. The persistence context (first-level cache) tracks managed entities per session/transaction; changes are flushed on commit via dirty checking.
LAZY vs EAGER fetching?
LAZY loads associations on first access (default for collections); EAGER loads immediately. Prefer LAZY plus fetch joins/projections to avoid over-fetching and N+1.
Why might @Transactional silently not work?
Self-invocation, non-public/final methods, not a Spring-managed bean, checked exception without rollbackFor, wrong @Transactional import (javax vs Spring), or an exception swallowed in a try/catch.

Production endpoints: /actuator/health, metrics, info, env, conditions... Expose selectively and secure them.
CAP theorem in one line?
In a network partition a distributed system must choose consistency or availability; you can't have all three of C, A and P.
Saga: choreography vs orchestration?
Choreography: services react to each other's events (decentralised, harder to follow). Orchestration: a central coordinator directs the steps and compensations (clearer, one more component).
