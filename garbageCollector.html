Must-Remember Key Points

  1. GC automatically reclaims memory of objects that are no longer reachable.
  2. Heap = Young Gen (Eden + Survivor S0/S1) + Old Gen (Tenured).
  3. New objects start in Eden. Eden full → Minor GC → survivors move to Survivor space.
  4. Objects surviving multiple GCs are promoted to Old Gen.
  5. Major GC = Old Gen (slower). Full GC = whole heap (+ Metaspace, depending on collector), the most expensive, may cause noticeable pauses.
  6. Garbage is detected by reachability analysis from GC Roots, not reference counting.
  7. obj = null only makes the object eligible for GC; it is not deleted immediately.
  8. System.gc() is just a request; avoid it (pauses, lower throughput).

1. What is GC & Heap Structure

Garbage Collection is the JVM process that automatically reclaims memory occupied by objects that are no longer reachable.

Young Generation
EdenSurvivor S0Survivor S1
Old Generation (Tenured)
Long-lived objects

All of the above sits inside the Heap.

Added
  • Why generations? Most objects die young (the "weak generational hypothesis"), so collecting the small Young Gen often is cheap and efficient.
  • Metaspace (native memory, replaced PermGen in Java 8) stores class metadata; it is outside the heap.
  • Heap vs stack: GC manages the heap. Stack frames are freed automatically when a method returns.
  • Stop-the-world (STW): GC pauses application threads for at least part of its work.

2. Object Lifecycle

Eden→ Minor GC →Survivor S0/S1→ survives multiple GCs →Old Gen
Step 1 · Creation 
Employee emp = new Employee();   // allocated in Eden
Step 2 · Minor GC

Triggered when Eden is full. The JVM removes dead objects and moves survivors Eden → Survivor.

Usually fast because most newly created objects die quickly.
Step 3 · Promotion

Objects that survive multiple GC cycles are promoted Survivor → Old Generation.

Added: how it really works
  • Each object has an age that increases per Minor GC survived. When it passes the tenuring threshold (max 15), it's promoted.
  • Survivors are copied between S0 and S1; one survivor space is always empty. Copying also compacts memory (no fragmentation in Young Gen).
  • If a survivor space is too full, objects can be promoted early. Very large objects may be allocated directly in Old Gen (or as "humongous" objects in G1).
  • Old Gen → Young Gen references are tracked using a card table / remembered set, so Minor GC doesn't scan the whole Old Gen.

Added: collectors & algorithms
  • Mark-Sweep-Compact: mark reachable objects, sweep unmarked ones, compact to remove fragmentation.
  • Serial: single-threaded, small apps. Parallel: multi-threaded, throughput-focused (Java 8 default).
  • G1: region-based, balances pause time and throughput (default since Java 9).
  • ZGC / Shenandoah: low-latency, mostly concurrent collectors for large heaps.
  • CMS was removed in Java 14.
  • "Major GC" is used loosely; precise meaning depends on the collector. Say "Old Gen collection" if asked to be exact.

4. How Does the JVM Decide an Object Is Garbage?

It uses Reachability Analysis starting from GC Roots:

  • Thread stacks
  • Static variables
  • Active threads
  • JNI references
If an object cannot be reached from any GC Root → eligible for GC.

Common misconception: obj = null

It does not immediately remove the object. It means eligible for GC, not deleted now. The JVM decides when to reclaim memory.

Added
  • Reference counting (used by some languages) fails on circular references. Reachability analysis handles cycles, so two objects pointing only at each other are still collected.
  • Local variables in active stack frames are also roots.
  • Reference types: strong (never collected while reachable), soft (collected under memory pressure; caches), weak (collected at next GC; e.g. WeakHashMap), phantom (post-collection cleanup).
  • finalize() is deprecated; prefer try-with-resources / Cleaner.

5. Why Avoid System.gc()?

System.gc();   // only a REQUEST to the JVM
It can trigger unnecessary GC, cause application pauses, and reduce throughput.

Modern JVM collectors are generally better at deciding when to run GC.

Interview-ready answer Java Garbage Collection automatically reclaims memory occupied by unreachable objects. New objects are created in the Young Generation, primarily in Eden Space. When Eden fills up, Minor GC runs and moves surviving objects to Survivor spaces. Objects that survive multiple GC cycles are promoted to the Old Generation. Major GC targets the Old Generation, while Full GC cleans the entire heap and is the most expensive operation. The JVM determines garbage using reachability analysis starting from GC Roots rather than simple reference counting.

6. Often-Missed Fundamentals

Added
  • Memory leaks still happen in Java: objects that stay reachable but are never used again (static collections, unremoved listeners, un-cleaned ThreadLocals, unbounded caches).
  • OutOfMemoryError appears when the JVM can't free enough memory, e.g. Java heap space or Metaspace.
  • Throughput vs latency: Parallel favours throughput; G1/ZGC aim for shorter pauses.
  • Common flags: -Xms/-Xmx (initial/max heap), -XX:+UseG1GC, -Xlog:gc (Java 9+) to log GC activity.
  • Reduce GC pressure: avoid unnecessary object creation in hot paths, reuse objects where sensible, size heap appropriately, and profile before tuning.

Quick Q&A (tap to reveal)

What is garbage collection?

The JVM process that automatically reclaims memory used by objects that are no longer reachable.

Describe the heap structure.

Young Gen (Eden, Survivor S0, Survivor S1) and Old/Tenured Gen.

What triggers a Minor GC?

Eden filling up. Dead objects are removed and survivors move to a Survivor space.

When does an object get promoted?

After surviving multiple GC cycles, it moves from Survivor to Old Gen.

Minor vs Major vs Full GC?

Minor: Young Gen, fast. Major: Old Gen, slower. Full: entire heap (+ Metaspace depending on collector), most expensive.

How does the JVM know an object is garbage?

Reachability analysis from GC Roots (thread stacks, statics, active threads, JNI refs). Unreachable means eligible.

Does obj = null free memory immediately?

No. It only makes the object eligible; the JVM decides when to reclaim it.

Why avoid System.gc()?

It's only a request but can trigger needless pauses and lower throughput; the JVM schedules GC better.

Why not reference counting?

It can't handle circular references; reachability analysis can.

Young objects die fast, old objects live long. Let the JVM decide when to collect.
