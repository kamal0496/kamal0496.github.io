Must-Remember Key Points

  1. Reverse proxy sits in front of servers and acts on their behalf: SSL termination, caching, compression, security filtering, simple routing.
  2. Forward proxy acts on behalf of clients (hides client identity); reverse proxy hides the servers.
  3. Load balancer distributes traffic across multiple servers, runs health checks and routes around failures → scalability + high availability.
  4. Algorithms: round robin, least connections, weighted, IP hash. L4 (TCP, fast, content-blind) vs L7 (HTTP-aware, content-based routing).
  5. API Gateway = reverse proxy that understands APIs: authentication, authorization, rate limiting, transformation, versioned routing, analytics.
  6. CDN = globally distributed reverse proxy caching static content near users.
  7. Roles overlap in real tools (Nginx, Kong, AWS ALB). Think in terms of problems solved, not product labels.
  8. Typical layering: CDN → API Gateway → Load Balancer → services → internal proxies/mesh. Don't over-engineer: small apps may only need a reverse proxy.

Edge → Reverse Proxy (edge concerns) → Load Balancer (distribution + failover) → API Gateway (API policies).

1The Problem: Exposing a Single Backend Directly

DefinitionA single application server exposed straight to the internet must do everything itself: encrypt/decrypt traffic, serve every request, fend off attacks and run business logic. As traffic grows, it becomes slow, fragile and a single point of failure.
  • SSL/TLS overhead: crypto handshakes consume CPU.
  • Traffic spikes: sudden surges overload the CPU.
  • No caching: identical requests repeatedly hit the app.
  • Security exposure: servers' IPs and ports are directly reachable (DDoS, malformed requests).
  • No failover: one server down means the system is down.
Client→Backend server (does everything)
Follow-up Why not just scale the backend vertically?
There is a ceiling, cost grows non-linearly, it remains a single point of failure, and it doesn't solve edge concerns (TLS, caching, filtering) cleanly. Horizontal scaling needs something to distribute traffic.

2Forward Proxy vs Reverse Proxy

DefinitionA forward proxy sits in front of clients and makes requests to the internet on their behalf. A reverse proxy sits in front of servers and receives requests from the internet on their behalf.
Forward proxyReverse proxy
Acts forClientsServers
HidesClient identity/IPServer identity/topology
Who configures itClient side (aware of it)Server side (transparent to clients)
Typical useCorporate filtering, anonymity, client-side cachingTLS termination, caching, load balancing, protection
Nuance VPNs are often mentioned with forward proxies, but a VPN creates an encrypted network-level tunnel for all traffic, whereas a forward proxy relays application-level requests (e.g. HTTP). They overlap in "hiding the client" but aren't the same thing.
Follow-up Which one does the client know about?
The forward proxy (client is configured to use it). A reverse proxy is transparent: the client thinks it is talking to the real server.

3Reverse Proxy

DefinitionA reverse proxy is a server that sits between clients and backend servers, accepts client requests on behalf of the backends, and forwards them, offloading generic edge work (TLS, caching, compression, filtering). It operates at the connection/routing layer and knows nothing about business logic or API rules.
  • SSL/TLS termination: decrypts at the proxy, so backends skip expensive crypto.
  • Caching: serves repeated identical responses without hitting the backend.
  • Compression: gzip/Brotli reduce bandwidth and speed delivery.
  • Security filtering: rate limiting, blocking malformed requests, hiding server IPs.
  • Tools: Nginx, HAProxy, Envoy, Caddy.
Added: example & concepts 
upstream app {
    least_conn;                                             # load-balancing algorithm
    server 10.0.0.1:8080 weight=3 max_fails=3 fail_timeout=30s;   # passive health check
    server 10.0.0.2:8080;
}
server {
    listen 443 ssl;
    ssl_certificate     /etc/ssl/site.crt;
    ssl_certificate_key /etc/ssl/site.key;
    gzip on;
    location /api/ {
        proxy_pass http://app;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;   # preserve client IP
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
  • Client IP: backends see the proxy's IP, so rely on X-Forwarded-For/X-Forwarded-Proto (in Spring Boot: server.forward-headers-strategy=framework).
  • TLS options: termination (decrypt at proxy), passthrough (L4, backend decrypts), re-encryption / mTLS to backends for zero-trust internal traffic.
  • Also: connection pooling/keep-alive to backends, buffering slow clients, static file serving, request IDs (X-Request-ID) for tracing, WAF integration.
Remember: a reverse proxy doesn't need multiple servers; with one backend it still gives security, TLS and caching.
Follow-up What's the security benefit of a reverse proxy?
Backend IPs/ports aren't exposed, malformed or abusive traffic is filtered early, and only the proxy needs hardened public exposure.
Follow-up What's the downside of TLS termination at the proxy?
Traffic between proxy and backend is plain unless you re-encrypt (mTLS). In sensitive environments, encrypt internal hops too.

4Load Balancer

DefinitionA load balancer distributes incoming requests across multiple backend servers, monitors their health, and stops sending traffic to failed ones, providing horizontal scalability, high availability and fault tolerance. It is essentially a reverse proxy specialised in intelligent traffic distribution.

Algorithms

AlgorithmHow it worksNote
Round RobinCycles through servers equallyAssumes identical servers
Least ConnectionsSends to server with fewest active requestsDynamic; good for uneven request cost
WeightedMore traffic to more powerful serversStatic weights
IP HashSame client IP → same backendSession affinity, but limits scalability/evenness

Layer 4 vs Layer 7

Layer 4 (transport)
  • Balances raw TCP/UDP connections
  • Doesn't inspect HTTP
  • Very fast, limited intelligence
Layer 7 (application)
  • Inspects headers, URLs, cookies
  • Content-based routing (e.g. /api/v2 → new service)
  • More flexible, more CPU
Nuance "Load balancers are reverse proxies" is true for L7 (they terminate the connection and open a new one to the backend). Many L4 balancers (NAT / direct server return) just forward packets and don't terminate connections, so they are not proxies in the strict sense.
Added
  • Health checks: active (LB probes /health periodically) and passive (marks a server bad after failed requests).
  • Sticky sessions (cookie or IP hash) vs stateless services: prefer stateless + shared session store (Redis/JWT) so any server can handle any request.
  • Connection draining: finish in-flight requests before removing a server (graceful deploys).
  • LB itself must be highly available: active-passive pair (VRRP/keepalived), managed cloud LB, or DNS/anycast. Otherwise it's a single point of failure.
  • Global load balancing: DNS-based/GSLB routes users to the nearest region. Types: hardware (F5), software (HAProxy, Nginx), cloud (AWS ALB/NLB, GCP LB).
  • AWS: ALB = L7, NLB = L4.
Follow-up A server is slow but not down. Which algorithm helps?
Least connections (or response-time based), since round robin keeps sending it equal traffic.
Follow-up How do you handle user sessions behind a load balancer?
Make services stateless: store sessions in Redis or use JWT. Sticky sessions work but hurt even distribution and failover.
Follow-up Isn't the load balancer a single point of failure?
Yes unless made redundant: multiple instances with failover (VRRP), managed cloud LBs, or DNS/anycast across several.
Follow-up When would you pick L4 over L7?
Non-HTTP protocols (databases, gRPC over raw TCP), maximum throughput/low latency, or TLS passthrough. L7 when you need path/header-based routing.

5API Gateway

DefinitionAn API gateway is a specialised reverse proxy that understands API semantics and is the single entry point for API clients. It centralises cross-cutting concerns (authentication, rate limiting, transformation, versioning, analytics) so individual microservices don't each duplicate them.

Why: in microservices, auth, rate limiting, logging, request transformation and versioning would otherwise be re-implemented in every service: inconsistent and hard to maintain.

  • Centralised authentication: token validation in one place.
  • Rate limiting/throttling: by client or tier.
  • Request/response transformation: backward compatibility, smooth API evolution.
  • Routing: by path, version or metadata (gradual migration, canary tests).
  • Analytics & observability: usage patterns, performance bottlenecks.
  • Tools: Kong, AWS API Gateway, Apigee, Tyk (also Spring Cloud Gateway).
Added 
spring:
  cloud:
    gateway:
      routes:
        - id: orders
          uri: lb://order-service                 # load-balanced via service discovery
          predicates: [ Path=/api/v1/orders/** ]
          filters:
            - StripPrefix=2
            - name: RequestRateLimiter            # token-bucket via Redis
              args: { redis-rate-limiter.replenishRate: 10, redis-rate-limiter.burstCapacity: 20 }
  • Rate limiting algorithms: fixed window, sliding window, token bucket (allows bursts), leaky bucket.
  • Auth split: authenticate (validate JWT/OAuth token) at the gateway; each service still authorises its own resources (zero trust).
  • Other features: request aggregation (fewer client round trips), response caching, circuit breaking, trace-ID injection, CORS, WAF, protocol translation (REST ↔ gRPC).
  • Pitfalls: it can become a bottleneck / single point of failure (run it clustered and stateless), and a "god component" if you put business logic in it. Keep it thin.
  • BFF (Backend-for-Frontend): a gateway tailored per client type (web/mobile).
  • North-south traffic (client ↔ system) goes through the gateway; east-west (service ↔ service) is handled by internal proxies/service mesh.
Follow-up API gateway vs load balancer?
A load balancer spreads traffic across identical instances (L4/L7). A gateway understands APIs: auth, rate limits, transformations, version routing. Gateways usually sit in front of load-balanced service instances.
Follow-up Should business logic live in the gateway?
No. Only cross-cutting infrastructure concerns; business rules belong in services.
Follow-up How do you avoid the gateway becoming a bottleneck?
Stateless horizontal scaling behind a load balancer, async/non-blocking stack (e.g. Netty), cache where possible, and keep filters lightweight.

6CDN (Content Delivery Network)

DefinitionA CDN is a globally distributed network of reverse proxies (edge servers) that caches and serves content close to users, cutting latency and shielding the origin from traffic spikes.
  • Caches and serves static content near the user; reduces latency.
  • Handles SSL termination early; absorbs spike traffic (and DDoS) before it hits core infrastructure.
Added
  • Cache control: driven by headers like Cache-Control: public, max-age=3600, ETag; versioned file names for cache busting; purge/invalidate when content changes.
  • Origin shield adds a mid-tier cache to reduce origin hits. Edge also provides WAF and bot protection.
  • Can accelerate some dynamic content via optimised routes, but personalised/non-cacheable requests still reach origin.
  • Examples: Cloudflare, Akamai, CloudFront, Fastly.
Follow-up How does a CDN decide what to cache?
By cache keys (URL/headers) and response headers (Cache-Control, Expires, Vary); configurable rules override them.

7Overlap, Spectrum & Real-World Layering

DefinitionThese three are best understood as a capability spectrum of the same underlying idea (a proxy) rather than rigid categories: each layer adds more intelligence for a different class of problem.
LayerAddsUnderstands
Reverse proxyEdge handling: TLS, caching, compression, filteringConnections / HTTP basics
Load balancerDistribution, health checks, failoverBackend health and load
API gatewayAuth, rate limits, transformation, versioning, analyticsAPI semantics and clients

Typical request path

Client→CDN (edge)→WAF / external LB→API Gateway→Internal LB→Service instances→Mesh sidecars
  • Static/cacheable content is answered at the CDN; dynamic requests go on.
  • The gateway enforces policies and routes; load balancers spread traffic across instances; internal proxies handle service-to-service concerns.

Tool overlap

  • Nginx: reverse proxy → also load balancer, and gateway with extra modules (OpenResty/Lua, NGINX Plus).
  • Kong: an API gateway built on Nginx, so also a reverse proxy and load balancer.
  • AWS ALB vs API Gateway: overlapping functions, different targets (ALB: traffic distribution to services; API Gateway: managed API features such as auth, throttling, usage plans).
Follow-up If Nginx can do all three, why distinguish them?
Because they solve different problems (edge handling, distribution/failover, API policy). Knowing the problem lets you choose and configure the right tool; the product label is secondary.

8Choosing the Right Tool

DefinitionPick the lightest layer that solves your current problem; add layers only when scale or requirements demand it.
SituationUse
Small app, one or few serversReverse proxy (Nginx/Caddy) for TLS, caching, compression
Need horizontal scaling and failoverLoad balancer
Public, API-driven platform for external clientsAPI gateway (auth, rate limits, transforms, analytics, versioning)
Global users / static assetsCDN
Very large microservice estateAll of the above + service mesh
Warning: not every system needs every layer. Over-engineering adds latency, cost and operational complexity. Each extra hop is another thing to monitor and to fail.
Follow-up A startup with 2 servers asks for Kong + service mesh. Your advice?
Start simple: a reverse proxy/cloud load balancer. Add a gateway when you have many services/external API clients needing central policies; add a mesh only at large scale.

9Service Mesh (Context)

DefinitionA service mesh is an infrastructure layer for service-to-service (east-west) communication, implemented with lightweight proxies (usually sidecars) next to each service instance, managed by a control plane.
Added
  • Provides: mutual TLS between services, retries/timeouts, circuit breaking, traffic splitting (canary), service-level metrics and tracing: without changing application code.
  • Examples: Istio and Linkerd (Envoy as the common data-plane proxy). Control plane configures; data plane (proxies) carries traffic.
  • Gateway vs mesh: gateway = north-south (edge, external clients); mesh = east-west (internal).
  • Trade-off: extra latency/resources and operational complexity; worthwhile mainly for large systems.
Follow-up Spring Cloud/Resilience4j vs service mesh for retries and circuit breaking?
Library: in-code, language-specific, fine-grained fallbacks. Mesh: language-agnostic and centrally managed but with less business-aware fallback logic. Many teams use one or the other, not both for the same concern.

🎯 More Core Questions (Recruiter Mode)

Answer out loud first, then tap to check.

Explain forward proxy vs reverse proxy in one sentence each.
Forward proxy represents clients to the internet; reverse proxy represents servers to clients.
What is SSL termination and why do it at the proxy?
Decrypting TLS at the edge so backends skip expensive crypto and certificates are managed centrally; re-encrypt to backends if internal traffic must be secure.
Active vs passive health checks?
Active: the LB periodically probes a health endpoint. Passive: it observes real traffic failures/timeouts and ejects bad servers.
What headers matter behind a proxy?
X-Forwarded-For (client IP), X-Forwarded-Proto (original scheme), X-Forwarded-Host, and a request/trace ID. Backends must trust them only from the proxy.
How do you do a zero-downtime deployment behind a load balancer?
Rolling or blue-green: drain connections from instances, deploy, health-check, then add back; or shift traffic gradually (canary) via weights/gateway routing.
How would you rate limit per client across multiple gateway instances?
Use a shared store (e.g. Redis) for counters/token buckets so all instances see the same state; local-only limits would multiply the allowed rate.
Where would you validate JWTs and where would you authorise?
Validate signature/expiry at the gateway; services still enforce authorisation (roles, ownership) for defence in depth.
What is a canary release and how does the gateway help?
Send a small percentage of traffic to a new version (weighted routing/header-based) and watch metrics before rolling out fully.
CDN vs reverse proxy?
A CDN is a globally distributed fleet of reverse proxies optimised for caching near users; a typical reverse proxy is a single site/regional component.
Design the edge for an e-commerce site at scale. Which layers and why?
CDN for static assets/edge TLS/DDoS → WAF → API gateway (auth, rate limits, routing, versioning) → load balancers over autoscaled services → internal proxies/mesh for mTLS and resilience. Add layers only as each problem appears.
Think in problems solved, not product labels: edge handling, distribution & failover, API policy.
