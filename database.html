Database Scaling: Replication & Sharding

Quick-revision cheat sheet for system design interviews.

Key PointsOverviewReplicationShardingCombinedTermsQuick Q&A

Must-Remember Key Points

  1. Replication = same data copied to many DBs → scales reads and gives availability. It does not solve huge datasets or write scaling.
  2. Sharding = data split across DBs → scales writes and data volume, but adds query/transaction complexity.
  3. Real systems combine both: shard router → shards, each with a leader + followers.
  4. Sync vs async replication is a consistency vs latency trade-off. Async can cause replication lag (stale reads).
  5. If the leader fails, a follower is promoted (failover).
  6. A good shard key is critical; poor choice → hotspots.
  7. Queries without the shard key need scatter-gather across shards.
  8. Cross-service consistency needs distributed transactions (2PC, Saga): next topic.

1. System Architecture & the Bottleneck

Client→API Gateway→Load Balancer→Microservices→Cache→Database
  • API Gateway: authentication, authorization, rate limiting, routing
  • Load Balancer: spreads requests across microservice instances
  • Cache: quick data access, fewer direct DB lookups
  • The microservice layer scales horizontally, but the database remains the bottleneck
Problem: scale the DB for millions of requests/sec and TB to 100+ TB of data while keeping availability and performance.

2. Replication

Multiple copies of the same database, to scale reads and improve fault tolerance.

2.1 Leader-Follower
  • Leader (primary): handles writes
  • Followers (read replicas): handle reads
  • Updates replicate from leader to followers (sync or async)
Writes→Leader→ replicates →Follower 1Follower 2Follower N←Reads
Example: out of 100,000 requests, 10,000 are writes (leader) and 90,000 are reads spread across followers.
2.2 Sync vs Async
TypeHow it worksProsConsConsistency
SynchronousLeader waits for follower ack before successStrong consistencyHigher write latency; failure-proneStrong
AsynchronousLeader replies immediately; replicates in backgroundLower latency, better availabilityReplication lag, possible inconsistencyEventual

Replication lag: followers temporarily serve stale data. Choose based on consistency vs latency needs.

2.3 Failover & Leader Election
  • Leader fails → promote a follower to leader
  • Automated by native DB tools or external coordination services
  • Keeps the system available and writes continuing
2.4 Leader-Leader (Multi-Master)
  • Multiple leaders accept writes independently; changes replicate bidirectionally
  • Better write availability (no single leader bottleneck)
Challenge: write conflicts from concurrent updates; needs conflict-resolution logic and is more complex. Less common than leader-follower.

3. Sharding (Horizontal Partitioning)

Replication copies data; sharding partitions it. Each shard is an independent DB instance holding a subset. This scales writes and data volume.

ShardExample range
Shard 1User ID 1 to 1,000,000
Shard 2User ID 1,000,001 to 2,000,000
Shard 3User ID 2,000,001 to 3,000,000

Shard Key & Strategies

The shard key (e.g. user ID) decides which shard stores a record. A good key gives even distribution and efficient queries.

Hash-based

Hash function on the shard key picks the shard.

Pro: even distribution
Con: hard range queries

Use: uniform access patterns

Range-based

Dataset divided into contiguous ranges.

Pro: easy range queries
Con: possible hotspots

Use: range queries, localized data

Hotspot Problem

Common with range-based sharding: new writes (e.g. sequential new user IDs) all land on the same shard → uneven load.

Query Complexity

Queries not using the shard key must hit multiple shards (scatter-gather), making cross-shard queries and transactions harder.

4. Combining Replication + Sharding

Large-scale systems use both for write scaling and read scaling with high availability.

App→Shard Router→Shard 1 (Leader + Followers)Shard 2 (Leader + Followers)Shard N (Leader + Followers)
ComponentRole
Shard RouterRoutes requests to the correct shard using the shard key
Shard's LeaderHandles all writes for that shard
Shard's FollowersServe read requests for that shard
Benefits: write scalability (data spread across shards), read scalability and availability (replication), large data volumes and high throughput.

5. Beyond DB Scaling

  • Business transactions span services and DBs (order, payment, inventory)
  • Consistency across them is hard; partial failures (payment OK, inventory reservation fails) need advanced handling

Quick Q&A (tap to reveal)

Replication vs sharding: what does each solve?

Replication scales reads and availability. Sharding scales writes and data volume.

Sync vs async replication?

Sync: strong consistency but higher write latency and failure-prone. Async: low latency and better availability, but replication lag and eventual consistency.

What happens when the leader dies?

Failover: a follower is promoted to leader, automated by DB tools or a coordination service.

Why is leader-leader less common?

Concurrent writes cause conflicts that need conflict-resolution logic, making it complex to manage.

Hash vs range sharding?

Hash gives even distribution but poor range queries. Range gives easy range queries but risks hotspots.

What is a hotspot and when does it occur?

One shard takes most writes, typically in range-based sharding with sequential IDs.

What is a scatter-gather query?

A query lacking the shard key, sent to multiple shards with results aggregated.

How do combined systems work?

A shard router sends each request to the right shard; within a shard, the leader takes writes and followers serve reads.

Replication + sharding = scalable, highly available, resilient databases.
