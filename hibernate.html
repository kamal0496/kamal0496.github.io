1What is Hibernate?

DefinitionHibernate is a Java ORM (Object-Relational Mapping) framework that maps Java classes to database tables, so you work with objects instead of hand-written SQL and ResultSet mapping. It is also the most popular implementation of the JPA (Jakarta Persistence) specification: JPA is the interface, Hibernate is the engine.
  • Without Hibernate (JDBC): open connections, write SQL strings, map rows to objects manually.
  • With Hibernate: map User to the users table; Hibernate generates the SQL.
Added
  • Benefits: less boilerplate, database portability (dialects), caching, lazy loading, dirty checking, schema/relationship mapping.
  • Costs: hidden SQL (N+1, over-fetching), learning curve, the "object-relational impedance mismatch" (inheritance, identity, associations).
  • Spring Data JPA sits on top: repositories use JPA's EntityManager, which Hibernate implements.
  • Packages: jakarta.persistence.* (Boot 3 / JPA 3) vs javax.persistence.* (older). Using JPA types keeps you vendor-neutral.
Follow-up JPA vs Hibernate vs Spring Data JPA?
JPA: specification (API). Hibernate: implementation with extra features. Spring Data JPA: abstraction that generates repository implementations on top of JPA.
Follow-up When would you avoid an ORM?
Heavy reporting, bulk/batch SQL, complex hand-tuned queries; use native SQL, jOOQ or JDBC templates for those parts.

2Entity & Mapping

DefinitionAn Entity is a plain Java class that Hibernate maps to a database table; each instance represents a row, identified by a primary key.
@Entity
@Table(name = "users")
public class User {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "full_name", nullable = false, length = 100)
    private String name;

    @Enumerated(EnumType.STRING)          // not ORDINAL
    private Status status;

    @OneToMany(mappedBy = "user", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Post> posts = new ArrayList<>();

    protected User() {}                   // JPA requires a no-arg constructor
}
Added
  • Entity rules: @Entity, an @Id, a no-arg constructor (≥ protected), non-final class/fields (Hibernate creates proxies by subclassing).
  • ID strategies: IDENTITY (DB auto-increment; disables JDBC insert batching), SEQUENCE (preferred on PostgreSQL/Oracle; allows batching), AUTO, TABLE (slow).
  • @Transient excludes a field; @Embeddable/@Embedded reuses value objects; @MappedSuperclass shares fields; @Inheritance (SINGLE_TABLE, JOINED, TABLE_PER_CLASS) maps hierarchies.
  • Always use EnumType.STRING so reordering an enum doesn't corrupt data.
Follow-up Why does Hibernate need a no-arg constructor and non-final classes?
It instantiates entities reflectively and generates lazy-loading proxies as subclasses; final classes/methods can't be proxied.
Follow-up IDENTITY vs SEQUENCE?
IDENTITY needs the INSERT executed immediately to get the id, blocking batching. SEQUENCE fetches ids ahead (allocation size) so inserts can be batched.

3SessionFactory & Session

DefinitionSessionFactory is Hibernate's heavyweight, thread-safe, application-wide object, built once at startup. Session is a lightweight, short-lived, not thread-safe unit of work used to talk to the database. JPA equivalents: EntityManagerFactory and EntityManager.
  • SessionFactory: created once; expensive. Session: created per operation/request; wraps a JDBC connection and holds the first-level cache.
try (Session session = sessionFactory.openSession()) {
    Transaction tx = session.beginTransaction();
    try { session.persist(user); tx.commit(); }
    catch (Exception e) { tx.rollback(); throw e; }
}
Correction SessionFactory isn't really "a factory for database connections". It is a factory for Sessions; it holds the compiled mapping metadata, the connection-provider/pool access, and the second-level cache. Connections come from the pool (HikariCP).
Added
  • In Spring you inject @PersistenceContext EntityManager: a shared proxy that binds to the current transaction's Session, so it's safe in singletons.
  • In Spring the persistence context is normally transaction-scoped (request-scoped with Open-Session-In-View).
  • session.unwrap(Session.class) / em.unwrap(Session.class) exposes Hibernate-specific API.
Follow-up Why is Session not thread-safe, and how does Spring cope?
It holds mutable state (persistence context, JDBC connection). Spring's EntityManager proxy resolves to a per-transaction (per-thread) instance.
Follow-up Why is SessionFactory expensive?
It parses mappings, builds metadata, SQL and caches at startup; create it once.

4Entity Lifecycle

DefinitionThe entity lifecycle describes an entity's relationship with the persistence context: Transient (new, unknown to Hibernate), Persistent/Managed (tracked by a Session), Detached (has a DB row but no Session), Removed (scheduled for deletion).
Transientpersist()Persistentdetach/clear/close →Detachedmerge() →Persistent
Persistentremove() →Removedflush/commit →DELETE
  • Transient: created with new, only in heap, no DB row. Exit: persist().
  • Persistent: tied to an active Session; dirty checking auto-generates UPDATEs at flush/commit. Enter via find()/get() or persisting a transient.
  • Detached: has a DB record but no Session; changes ignored. Enter via detach(), clear(), close(). Re-attach with merge() (use the returned instance).
  • Removed: object still exists in memory; DELETE runs at next flush/commit.
Employee emp = new Employee();       // Transient
emp.setName("Alice");
session.persist(emp);                // Persistent
emp.setSalary(90000);                // synced to DB at commit
session.detach(emp);                 // Detached
emp.setSalary(95000);                // ignored
Employee managed = session.merge(emp);   // new managed copy carries the change
session.remove(managed);             // Removed (DELETE pending)
Corrections / nuance
  • save(), saveOrUpdate(), update(), delete(), get(), load() are legacy Hibernate-native methods (deprecated in Hibernate 6). Prefer JPA-standard persist, merge, remove, find, getReference.
  • "Transient has no primary key" is the usual case, but entities with assigned IDs can have an id yet still be transient (unknown to the session).
  • merge() doesn't re-attach your object. It copies its state onto a managed instance (loading it if needed) and returns that.
Added
  • persist vs save: persist returns void and is JPA-standard; save returns the id. With IDENTITY, the INSERT happens immediately; with SEQUENCE it's deferred to flush.
  • Calling persist() on a detached entity throws PersistenceException ("detached entity passed to persist").
  • refresh() reloads state from the DB, discarding unflushed changes.
Follow-up What does merge() do on a detached entity with changes?
Loads the managed entity with that id, copies the detached state onto it, and returns the managed instance; the original object stays detached.
Follow-up You modify a detached entity and nothing is saved. Why?
Hibernate only tracks managed entities. Call merge() inside a transaction (or load, modify, commit within one transaction).
Follow-up Does remove() delete the row immediately?
No, it schedules a DELETE executed at flush/commit.

5Dirty Checking & Automatic Flushing

DefinitionDirty checking is Hibernate's mechanism of detecting changes to managed entities automatically: it keeps a snapshot of each loaded entity, and at flush time compares current state to the snapshot, generating UPDATE statements for changed fields.
User user = session.get(User.class, 1L);
user.setName("New Name");          // no explicit save needed
// commit → UPDATE users SET full_name='New Name' WHERE id=1
  • The snapshot lives in the L1 cache (persistence context). Triggered at flush() or transaction commit.
Added
  • Flush ≠ commit: flush synchronises SQL with the DB inside the transaction (still rollback-able); commit makes it permanent.
  • Flush modes: AUTO (default; flushes before commit and before queries that might be affected), COMMIT, MANUAL (only on explicit flush(); used by readOnly=true).
  • Hibernate updates all columns by default; @DynamicUpdate only updates changed ones (wide tables).
  • Cost: dirty checking compares every managed entity at flush; many loaded entities = slow. Use read-only transactions, projections, or clear() in batch jobs.
Follow-up Why does a read-only query method perform better?
No flush and no dirty-check pass, and entities may be loaded without snapshots.
Follow-up You changed an entity, then ran a JPQL query. Is the change visible to it?
Yes with FlushMode AUTO: Hibernate flushes pending changes before executing the query so results are consistent.

6Relationships & Fetch Types

DefinitionRelationship annotations map associations between entities to foreign keys: @OneToOne, @OneToMany, @ManyToOne, @ManyToMany. Fetch type decides when related data loads: LAZY on first access, EAGER immediately.
@Entity class Post {
    @ManyToOne(fetch = FetchType.LAZY) @JoinColumn(name = "user_id")   // OWNING side (holds the FK)
    private User user;
}
@Entity class User {
    @OneToMany(mappedBy = "user", cascade = CascadeType.ALL, orphanRemoval = true)  // inverse side
    private List<Post> posts = new ArrayList<>();
    void addPost(Post p) { posts.add(p); p.setUser(this); }   // keep both sides in sync
}
Missing detail "Default is lazy for collections" is true, but @ManyToOne and @OneToOne default to EAGER, a frequent cause of hidden N+1 queries. Explicitly set fetch = LAZY on them.
Added
AnnotationDefault fetch
@OneToManyLAZY
@ManyToManyLAZY
@ManyToOneEAGER
@OneToOneEAGER
  • Owning vs inverse side: the side with the foreign key (the "many" side) owns the relationship; mappedBy marks the inverse side. Only the owning side's changes are persisted.
  • Cascade propagates operations (PERSIST, MERGE, REMOVE, ALL). orphanRemoval deletes children removed from the collection.
  • Prefer Set for @ManyToMany; avoid CascadeType.REMOVE/ALL on @ManyToMany. Prefer a bidirectional @OneToMany with a @ManyToOne owner over unidirectional @OneToMany (extra join table/updates).
  • Avoid toString()/JSON on both sides of a bidirectional link (infinite recursion).
Follow-up What is mappedBy?
It marks the inverse side and names the field on the owning side that holds the foreign key, so no duplicate join column/table is created.
Follow-up Why is EAGER usually a bad default?
It always loads associations, even when unused, producing extra queries/joins and cartesian products; choose LAZY and fetch explicitly per use case.

7HQL / JPQL

DefinitionJPQL (JPA) and HQL (Hibernate's superset) are object-oriented query languages: you query entity classes and their fields, not tables and columns, and Hibernate translates them into SQL for the target database.
List<User> users = session.createQuery(
        "select u from User u where u.email = :email and u.status = :status", User.class)
    .setParameter("email", email)            // always bind parameters (no SQL injection)
    .setParameter("status", Status.ACTIVE)
    .getResultList();

// Spring Data JPA
@Query("select u from User u join fetch u.posts where u.id = :id")
Optional<User> findWithPosts(@Param("id") Long id);
Added
  • Alternatives: Criteria API (type-safe, dynamic), native SQL (createNativeQuery), Spring Data derived queries/Specifications.
  • HQL is database-agnostic; native isn't. Bulk UPDATE/DELETE in HQL bypass the persistence context (entities in L1 can become stale).
  • Projections: select new com.app.UserDto(u.id, u.name) from User u or interface/record projections avoid loading full entities.
  • Pagination: setFirstResult()/setMaxResults().
Follow-up JPQL vs native SQL?
JPQL: portable, entity-based, supports fetch joins. Native: DB-specific features/performance, returns raw rows or mapped results, less portable.
Follow-up How do you prevent SQL injection?
Use named/positional parameters; never concatenate user input into the query string.

8The N+1 Problem

DefinitionThe N+1 problem occurs when you run 1 query to load N parent entities, then trigger N additional queries (one per parent) as you access a lazy association in a loop.
List<User> users = em.createQuery("select u from User u", User.class).getResultList(); // 1 query
for (User u : users) {
    u.getPosts().size();        // +1 query per user → N more
}

The 3 solutions

// 1. JOIN FETCH (most common)
select distinct u from User u join fetch u.posts

// 2. @EntityGraph (JPA standard)
@EntityGraph(attributePaths = "posts")
List<User> findAll();

// 3. @BatchSize (Hibernate-specific): load children in batches instead of one by one
@BatchSize(size = 20)
@OneToMany(mappedBy = "user") private List<Post> posts;
// or globally: spring.jpa.properties.hibernate.default_batch_fetch_size=20

Detect it: enable SQL logging in development and look for repeated selects.

spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true
logging.level.org.hibernate.type.descriptor.sql=TRACE
Corrections
  • DISTINCT: needed to de-duplicate parents in Hibernate 5. Hibernate 6 de-duplicates entity results automatically, so DISTINCT is no longer required (it's harmless).
  • Logging property: org.hibernate.type.descriptor.sql=TRACE is the Hibernate 5 way to see bound parameters. In Hibernate 6 use logging.level.org.hibernate.SQL=DEBUG and logging.level.org.hibernate.orm.jdbc.bind=TRACE (show-sql prints to stdout, not the logger).
Added
  • Other fixes: DTO projections (fetch only what you need), @Fetch(FetchMode.SUBSELECT), and making @ManyToOne/@OneToOne LAZY.
  • Pitfalls of JOIN FETCH on collections: pagination is applied in memory (warning HHH000104); fetching two List collections throws MultipleBagFetchException (use Set, or fetch in separate queries). Each extra collection join multiplies rows (cartesian product).
  • Production detection: Hibernate statistics (hibernate.generate_statistics), datasource-proxy, or APM query counts; assert query counts in tests.
Follow-up Why does paging with JOIN FETCH on a collection misbehave?
The join multiplies parent rows, so the DB can't limit parents; Hibernate loads everything and paginates in memory. Page parent IDs first, then fetch children for those IDs.
Follow-up JOIN FETCH vs @EntityGraph vs @BatchSize: when each?
JOIN FETCH/EntityGraph: one query, best for a known needed association (watch cartesian products). BatchSize: cheaper to apply broadly, a few batched queries instead of N.
Follow-up Can EAGER cause N+1 too?
Yes. With find() eager associations are joined, but JPQL queries load parents first and then fetch eager associations with separate selects, causing N+1.

9First-Level (L1) Cache

DefinitionThe L1 cache is the persistence context built into every Session/EntityManager. It is always on and guarantees that within one session an entity with a given primary key is loaded once and is the same Java object every time.
Session session = sessionFactory.openSession();
User u1 = session.get(User.class, 1L);   // SELECT fired
User u2 = session.get(User.class, 1L);   // NO query: served from L1
System.out.println(u1 == u2);            // true: same object
  • Also stores the snapshot used for dirty checking. Cleared when the Session closes, so it helps within a request but not across requests.
  • session.evict(user) removes one entity; session.clear() wipes the cache.
  • Bulk inserts: call flush() then clear() periodically so L1 doesn't grow and slow down.
for (int i = 0; i < 100_000; i++) {
    session.persist(new Item(i));
    if (i % 50 == 0) { session.flush(); session.clear(); }   // match hibernate.jdbc.batch_size=50
}
Added
  • L1 serves lookups by primary key (find). A JPQL query always hits the DB, though returned rows resolve to the already-managed instances.
  • In Spring the persistence context is scoped to the transaction (or to the whole request with Open-Session-In-View).
  • Batch inserts also need hibernate.jdbc.batch_size and a non-IDENTITY id strategy.
  • Memory risk: loading huge result sets into one session; use pagination/streaming and clear().
Follow-up Does a second em.find() in a different transaction hit the DB?
Yes: a new transaction has a new persistence context (empty L1). Only L2 could serve it.
Follow-up Why can bulk JPQL updates leave stale entities?
They execute directly in the DB and bypass L1; managed entities keep old values until refreshed/cleared (@Modifying(clearAutomatically = true)).

@org.hibernate.annotations.Cache(usage = CacheConcurrencyStrategy.READ_WRITE)
public class Country { ... }
  • Concurrency strategies: READ_ONLY (never changes), NONSTRICT_READ_WRITE, READ_WRITE (soft locks; common), TRANSACTIONAL (JTA).
  • Query cache is separate: caches result ids per query + parameters (setCacheable(true)); invalidated when the queried tables change. Collections need their own @Cache.
  • Best for: read-mostly reference data (countries, config). Avoid for: frequently updated data.
  • Pitfalls: stale data in clusters without a distributed/invalidating provider; native or bulk SQL may bypass or flush regions; extra memory; harder debugging.
Follow-up What exactly does L2 store?
The "dehydrated" column values keyed by id, not entity instances; each session rebuilds its own entity objects from that state.
Follow-up Would you enable L2 by default? Why/why not?
No. Enable selectively for read-mostly data after measuring; otherwise it adds staleness risk and memory cost for little gain.
Follow-up L2 cache vs Spring Cache (@Cacheable)?
L2 caches entity state transparently inside Hibernate; Spring Cache caches method results (any objects/DTOs) at the service layer with explicit control.

11Transaction Propagation

DefinitionPropagation controls what happens when a @Transactional method is called while a transaction already exists: join it, start a new one, suspend it, or refuse to run.
Added (your notes cut off here)
TypeBehaviour
REQUIRED (default)Join existing, else create new
REQUIRES_NEWAlways new; suspends the outer transaction
SUPPORTSJoin if exists, else run without
NOT_SUPPORTEDRun without a transaction (suspends existing)
MANDATORYMust exist, else exception
NEVERMust not exist, else exception
NESTEDSavepoint within the outer transaction
 
@Transactional
public void placeOrder(Order o) {
    orderRepo.save(o);
    audit.log(o);                      // REQUIRES_NEW: its own transaction and commit
}
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void log(Order o) { auditRepo.save(new Audit(o)); }
  • Hibernate angle: the Session/persistence context is bound to the transaction. REQUIRED shares one persistence context; REQUIRES_NEW gets a new one, so entities loaded in the outer one aren't managed in the inner one, and it uses a second DB connection.
  • Only RuntimeException/Error roll back by default; checked exceptions need rollbackFor.
  • It's proxy-based: self-invocation bypasses it.
  • An inner REQUIRED failure marks the shared transaction rollback-only → UnexpectedRollbackException at outer commit.
Follow-up A same-class method with REQUIRES_NEW is called via this. What happens?
It runs in the existing transaction: self-invocation skips the proxy. Move it to another bean.
Follow-up REQUIRES_NEW vs NESTED?
REQUIRES_NEW: independent transaction/connection that commits on its own. NESTED: savepoint inside the outer transaction; rolls back with it.

12Isolation Levels

DefinitionIsolation controls what a transaction can see of changes made by other concurrent transactions. Higher isolation prevents more anomalies but costs concurrency.
Added (your notes cut off here)
LevelDirty readNon-repeatable readPhantom read
READ_UNCOMMITTEDPossiblePossiblePossible
READ_COMMITTEDPreventedPossiblePossible
REPEATABLE_READPreventedPreventedPossible*

  • *InnoDB/PostgreSQL prevent phantoms at REPEATABLE_READ via snapshots/gap locks. Defaults: PostgreSQL/Oracle/SQL Server = READ_COMMITTED; MySQL InnoDB = REPEATABLE_READ.
  • Dirty read: reading uncommitted data. Non-repeatable: same row, different values. Phantom: same query, different rows.
@Transactional(isolation = Isolation.REPEATABLE_READ)
public void transfer(long from, long to, BigDecimal amt) { ... }

Beyond isolation: concurrency control in Hibernate (lost updates):

@Entity class Account { @Version private Long version; ... }       // optimistic locking
// UPDATE account SET ..., version=2 WHERE id=? AND version=1  → OptimisticLockException if stale

em.find(Account.class, id, LockModeType.PESSIMISTIC_WRITE);        // SELECT ... FOR UPDATE
  • Optimistic: no DB lock; detect conflicts at commit (best for low contention). Pessimistic: lock rows up front (high contention, short transactions).
Follow-up Two users edit the same record. How do you stop silent overwrite?
Add @Version for optimistic locking; the second commit fails with OptimisticLockException and the app retries or informs the user.
Follow-up Which isolation level would you choose and why?
Usually the DB default (READ_COMMITTED) plus optimistic locking where needed; raise isolation only for specific consistency-critical flows.

🎯 More Core Hibernate Concept Questions (Recruiter Mode)

Answer out loud first, then tap to check.

Persistence Basics

get()/find() vs load()/getReference()?
find hits the DB immediately and returns null if missing. getReference returns a lazy proxy without querying (throws EntityNotFoundException on first access if missing); handy for setting a foreign key without loading the entity.
persist vs save vs merge vs update vs saveOrUpdate?
persist: JPA, makes a new entity managed (void). save: Hibernate legacy, returns id. merge: copies state onto a managed instance (new or detached) and returns it. update/saveOrUpdate: legacy re-attach of the same instance.
What is LazyInitializationException and how do you fix it?
Accessing a lazy association after the Session closed. Fix: fetch what you need inside the transaction (JOIN FETCH, EntityGraph, DTO projection) or map to DTOs in the service layer. Don't switch everything to EAGER.
What is Open-Session-In-View (OSIV)? Pros and cons?
Keeps the Session open through the whole web request (Boot default spring.jpa.open-in-view=true), so lazy loading works in controllers/views. Cons: hidden queries outside the service layer, connection held longer (pool pressure). Many teams disable it.
Entity vs DTO: why not expose entities from controllers?
Entities are tied to the persistence model (lazy proxies, bidirectional cycles, over-exposure of fields). DTOs give a stable API contract and control exactly what's fetched.

Mapping Details

How should equals()/hashCode() be implemented on entities?
Avoid using all fields or a generated id that is null before persist. Use a stable business key, or an id-based equals that handles null (and a constant hashCode for the class). Needed for correct behaviour in Sets and across detached instances.
Inheritance mapping strategies?
SINGLE_TABLE (one table, fast, nullable columns), JOINED (normalised, joins), TABLE_PER_CLASS (union queries, rarely used). @MappedSuperclass shares fields without being an entity.
Cascade types and orphanRemoval?
PERSIST, MERGE, REMOVE, REFRESH, DETACH, ALL propagate operations to children. orphanRemoval=true deletes children removed from the parent's collection. Use only for true parent-child ownership.
What is @Embeddable? @Transient?
@Embeddable/@Embedded: a value object whose fields are stored in the owner's table (e.g. Address). @Transient: field not persisted.

Performance & Concurrency

How do you do efficient batch inserts/updates?
Set hibernate.jdbc.batch_size, use SEQUENCE ids (IDENTITY blocks batching), order inserts/updates, and flush()+clear() every batch to keep L1 small.
Optimistic vs pessimistic locking?
Optimistic uses a @Version column and detects conflicts at commit (scalable, retry on failure). Pessimistic locks rows (FOR UPDATE) to block others (safer under heavy contention, risks deadlocks/waiting).
Why can fetching two List collections fail?
MultipleBagFetchException: Hibernate can't fetch multiple unordered bags in one query. Use Set, @OrderColumn, or separate queries.
How do you view/measure Hibernate's SQL in production-like environments?
SQL logging via logger categories, Hibernate statistics, a datasource proxy, or APM tracing; add query-count assertions in tests to catch regressions.
Hibernate Session vs JDBC Connection?
A Session wraps a connection plus a persistence context (L1 cache, snapshots, action queue). It borrows a connection from the pool when needed and releases it afterwards.
Define it clearly, show a small example, state the trade-off, and be ready for the follow-up.
