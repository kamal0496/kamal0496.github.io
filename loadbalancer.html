What & Why

A load balancer is an intelligent intermediary between clients and a pool of servers. It receives every incoming request and decides which server handles it, like a traffic police officer sending vehicles to less crowded roads.

  • Spreads requests so no single server is overwhelmed
  • Gives high availability, fault tolerance and better performance under spikes (e.g. a Cricket World Cup final)
  • Without it, traffic bottlenecks on one server → failure or degraded UX

What it monitors

Availabilityis the server up?
Health / statusis it responding well?
Current loadactive connections

It combines these signals with the configured routing algorithm to pick a server per request.

The 4 Routing Algorithms

1 · Round Robin

Requests go to servers in a circle; after the last server it wraps to the first.

Req 1 → AReq 2 → BReq 3 → CReq 4 → DReq 5 → A (repeat)
Pros: simple, easy to implement.
Cons: assumes identical servers; ignores health and load; may overload a slow server.
2 · Weighted Round Robin

Each server gets a weight proportional to its capacity; stronger servers get more requests.

A · 32 CPUweight 4
B · 16 CPUweight 3
C · 8 CPUweight 2
D · 4 CPUweight 1

Distribution: 4 requests to A, then 3 to B, 2 to C, 1 to D, and repeat.

Pros: suits heterogeneous servers.
Cons: static; doesn't watch real-time CPU or connections, so a busy powerful server can still be overloaded while weaker ones sit idle.
3 · Least Connections

Each new request goes to the server with the fewest active connections.

Pros: dynamic, accounts for real-time load and availability; more adaptive than the round-robin variants.
Cons: needs the balancer to continuously track connection counts.
4 · IP Hash (Sticky Sessions)

Hash of the client IP picks the server, so a given IP always lands on the same server. Also called session affinity.

Pros: keeps session state consistent without shared session storage.
Cons: can distribute unevenly; ties users to one server.

Remember: no algorithm is universally best. Production systems often default to round robin or least connections and add sticky sessions only when needed; hybrids are common.

Session Consistency Problem

If requests from one user bounce between servers, session state breaks.

Example: user adds items to the cart on Server B; on refresh the request hits Server C, which has no session data → the cart looks empty.

Fix: IP hash / sticky sessions route that user to the same server every time. This matters when session data is stored locally on a server rather than in a central store.

Quick Q&A (tap to reveal)

Why use a load balancer?

To distribute traffic, avoid single-server overload, and get availability, fault tolerance and performance at scale.

When would round robin fail you?

When servers differ in capacity or health: it sends equal traffic to a slow or overloaded node.

Weighted RR vs Least Connections?

Weighted RR uses static, pre-set capacity weights. Least Connections reacts to real-time active connections.

When do you need sticky sessions?

When session data lives locally on each server and the user must keep hitting the same one.

Which algorithm do most apps default to?

Round robin for simplicity; some choose least connections for better adaptation.

Load balancers keep large-scale systems reliable and scalable under heavy traffic.
