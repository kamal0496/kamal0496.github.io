1 Core Concepts

Why Kafka exists

Point-to-point integrations between many systems become a tangled mess, and traditional queues/DBs struggle with very high throughput, replay and fan-out. Kafka is a distributed, durable, append-only commit log acting as a central event backbone.

  • Decouples producers from consumers (async, independent scaling)
  • Handles millions of events/sec with horizontal scale
  • Durable and replayable: messages are retained by time/size, not deleted on consumption
  • Multiple independent consumers can read the same data

Use cases: event streaming, log aggregation, CDC, payments/transaction events, metrics, event sourcing.

What are partitions, and why partitions?

A topic is split into partitions; each is an ordered, immutable, append-only log stored on a broker.

  • Scalability: data spread across brokers
  • Parallelism: one consumer per partition within a group; max parallelism = partition count
  • Throughput: parallel writes and reads
Note: Partitions can be increased but never decreased, and increasing breaks key→partition mapping for existing keys.
Ordering guarantee

Kafka guarantees order only within a single partition, never across partitions of a topic.

  • Need ordering per entity (e.g. account)? Use the entity ID as the message key so all its events land in one partition.
  • Global ordering = 1 partition (sacrifices parallelism).
  • With retries, set enable.idempotence=true (or max.in.flight.requests.per.connection ≤ 5) to avoid reordering.
What is an offset?

A sequential, immutable number identifying a record's position within a partition. Uniqueness is the triple (topic, partition, offset).

Why offsets matter
  • Consumers track progress by committing offsets (stored in __consumer_offsets)
  • Enable resume after crash/restart without data loss
  • Enable replay: reset offsets to reprocess (bug fix, new service)
  • Define delivery semantics: commit timing decides at-least-once vs at-most-once
  • Committed offset = next record to read (last processed + 1)

2 Consumer Groups

What is a consumer group?

A set of consumers sharing a group.id that cooperatively consume a topic. Partitions are divided among members, so each message is processed by one consumer in the group. Different groups each get the full stream (pub/sub).

Consumer group rule

One partition is consumed by at most one consumer within a group at a time (a consumer may own many partitions).

ScenarioResult
Consumers < partitionsSome consumers handle multiple partitions
Consumers = partitions1:1, max parallelism
Consumers > partitionsExtra consumers sit idle
Rebalancing

Redistribution of partitions among group members. Triggered by: consumer joins/leaves/crashes, missed heartbeat or poll timeout, topic partition count change, subscription change.

  • Eager: all consumers revoke everything, then reassign ("stop-the-world")
  • Cooperative (incremental): only affected partitions move; prefer CooperativeStickyAssignor

Costs: processing pause, duplicate processing if offsets weren't committed. Deep dive in section 6.

Message key and partition selection
  • Key present: partition = murmur2(keyBytes) % numPartitions, so same key → same partition → ordered
  • No key: sticky partitioner, fills a batch for one partition then switches (older: round-robin)
  • Custom: implement Partitioner
  • Explicit partition in ProducerRecord overrides all
Watch for: hot partitions from skewed keys; changing partition count remaps keys.

3 Brokers & Replication

What is a broker?

A Kafka server that stores partition data on disk and serves producers/consumers. A cluster = multiple brokers; each partition lives on several brokers. Cluster metadata and controller election are handled by KRaft (ZooKeeper in legacy versions).

Replication

Each partition is copied to replication.factor brokers for fault tolerance. Production standard: RF = 3.

Leader and followers
  • Leader: one replica per partition handling all reads/writes
  • Followers: fetch from the leader to stay in sync (hot standby)
  • Leaders are spread across brokers for load balance
What happens if the leader crashes?
  1. Controller detects broker failure
  2. Elects a new leader from the ISR
  3. Clients refresh metadata and redirect to the new leader

If ISR is empty: with unclean.leader.election.enable=false (default) the partition is unavailable; with true an out-of-sync replica may lead, risking data loss. Trade-off: consistency vs availability.

In-Sync Replicas (ISR)

The set of replicas (leader included) that are caught up with the leader within replica.lag.time.max.ms. Slow or dead followers are dropped from ISR and rejoin after catching up.

min.insync.replicas: minimum ISR size required to accept writes with acks=all. Else the producer gets NotEnoughReplicas.

Durable setup: RF=3, min.insync.replicas=2, acks=all. Survives one broker loss with no data loss.

4 Performance & Guarantees

Why is Kafka fast?
  • Sequential disk I/O (append-only log), comparable to memory-speed for sequential access
  • OS page cache instead of heap caching; no GC pressure
  • Batching of records on produce and fetch
  • Compression per batch
  • Zero-copy transfer
  • Partitioned parallelism
  • Simple dumb-broker/smart-client design, with binary protocol
Zero-copy transfer

Uses sendfile() (Java FileChannel.transferTo) to move data from the page cache straight to the network socket in kernel space, skipping copies to user-space and context switches.

Traditional: disk → kernel buf → app buf → socket buf → NIC
Zero-copy  : disk → page cache ────────────────→ NIC

Caveat: Not applicable with TLS encryption, since data must pass through user space.

For external side effects (DB, REST), use idempotency keys or the outbox pattern.

5 Producer Deep Dive

Producer architecture
send() → Serializer → Partitioner → RecordAccumulator (per-partition batches)
                                          ↓
                             Sender thread (background) → Broker

send() is async; it returns a Future/callback. The main thread appends to a buffer, and a separate I/O Sender thread ships batches.

Producer buffer
  • buffer.memory (default 32MB): total memory for unsent records
  • If full, send() blocks up to max.block.ms, then throws TimeoutException
  • Signals producer is faster than broker/network
Batching
  • batch.size (16KB): max bytes per partition batch
  • linger.ms (0; set 5–20): wait to fill batch before sending
  • Larger batches → higher throughput, slightly higher latency
Compression

compression.type: none | gzip | snappy | lz4 | zstd. Applied per batch, so it works better with bigger batches. Brokers store compressed; consumers decompress. lz4/zstd are common picks (speed vs ratio).

Retries
  • retries (default huge) bounded by delivery.timeout.ms (120s default)
  • retry.backoff.ms between attempts
  • Retriable: network errors, leader election. Non-retriable: record too large, serialization.
  • Risks: duplicates and reordering without idempotence
Idempotent producer

enable.idempotence=true (default since Kafka 3.0). Broker dedupes using Producer ID (PID) + sequence number per partition, so retries don't create duplicates and ordering is preserved. Requires acks=all, retries>0, max.in.flight ≤ 5.

Scope: single producer session, single partition. Cross-partition atomicity needs transactions (transactional.id).

# Recommended durable producer
acks=all
enable.idempotence=true
linger.ms=10
batch.size=32768
compression.type=lz4
delivery.timeout.ms=120000

6 Consumer Deep Dive

Consumer architecture & poll model

Consumers pull (not push), controlling their own pace and backpressure. The loop:

while (true) {
  records = consumer.poll(Duration.ofMillis(500));
  for (r : records) process(r);
  consumer.commitSync();
}

poll() fetches records, sends heartbeats via a background thread, and participates in group coordination. Single-threaded: KafkaConsumer is not thread-safe.

Consumer lag & why it matters

Lag = log-end offset − committed offset, per partition.

  • Growing lag = consumers can't keep up → delayed processing, stale data
  • If lag exceeds retention, data is deleted before it's read → permanent loss
  • Primary health/SLA metric; monitor with Burrow, Prometheus, kafka-consumer-groups.sh --describe
  • Fixes: add consumers (≤ partitions), speed up processing, increase partitions, tune fetch settings
Heartbeats

A background thread sends heartbeats to the group coordinator every heartbeat.interval.ms (3s, ≈ ⅓ of session timeout) to prove liveness.

Rebalancing deep dive
  1. Group coordinator (a broker) detects change
  2. Members rejoin (JoinGroup); one becomes group leader
  3. Leader computes assignment (assignor); coordinator distributes (SyncGroup)

Mitigation: cooperative-sticky assignor, static membership (group.instance.id) so restarts don't trigger rebalance, tune timeouts, keep processing fast, commit in onPartitionsRevoked.

session.timeout.ms vs max.poll.interval.ms
SettingDetectsDefault
session.timeout.msConsumer process dead (no heartbeats)45s
max.poll.interval.msConsumer stuck/slow (too long between poll() calls)5 min

Exceeding either → consumer removed → rebalance → CommitFailedException on late commit. Slow processing is the usual culprit: reduce max.poll.records or raise the interval.

Fetching records & max.poll.records
  • fetch.min.bytes / fetch.max.wait.ms: broker waits for min data or timeout
  • fetch.max.bytes, max.partition.fetch.bytes: size caps
  • max.poll.records (500): max records returned per poll(). This is the knob for per-batch processing time.
Consumer concurrency
  • Scale by more consumers in the group (≤ partitions)
  • Or multiple threads: one consumer per thread, or a consumer + worker pool (careful with offset commits and ordering)
  • Spring: concurrency on the listener container = N consumer threads
Offset management revisited
  • Auto-commit (enable.auto.commit=true, every 5s): simple but can lose or duplicate on crash
  • commitSync: blocking, reliable, retries
  • commitAsync: faster, no retry (ordering risk); use sync on shutdown
  • Per-record / per-partition commits for finer control
  • auto.offset.reset: earliest | latest | none applies only when no committed offset exists
  • seek() to replay/skip manually
Rule: Commit after successful processing for at-least-once; store offsets with business data in the same DB transaction for effectively-once.

7 How Spring Kafka Works

You write
@Service
class PaymentConsumer {
  @KafkaListener(topics = "payments", groupId = "payment-svc", concurrency = "3")
  public void handle(PaymentEvent event, Acknowledgment ack) {
    process(event);
    ack.acknowledge();
  }
}

kafkaTemplate.send("payments", accountId, event); // key = accountId
Under the hood, Spring creates
  • KafkaListenerAnnotationBeanPostProcessor scans @KafkaListener methods and registers endpoints
  • ConcurrentKafkaListenerContainerFactory builds containers
  • ConcurrentMessageListenerContainer → spawns N child KafkaMessageListenerContainers (= concurrency), each with its own KafkaConsumer thread
  • Each container runs the poll loop, deserializes, invokes your method via a message adapter, then handles offset commits per AckMode
  • KafkaTemplate wraps KafkaProducer (from ProducerFactory); send() returns CompletableFuture<SendResult>
AckModeCommit
BATCH (default)After all records from a poll are processed
RECORDAfter each record
MANUAL / MANUAL_IMMEDIATEWhen you call ack.acknowledge()
TIME / COUNTPeriodically / after N records

Note: Spring sets enable.auto.commit=false by default and manages commits itself. Concurrency can't usefully exceed partition count.

8 Error Handling, Retry & DLT

Error handling

Spring Kafka uses DefaultErrorHandler (replaced SeekToCurrentErrorHandler). When the listener throws, the container seeks back to the failed record's offset and re-delivers it, so records aren't lost, and the rest of the batch is reprocessed.

  • Deserialization errors: wrap with ErrorHandlingDeserializer, otherwise the poll loop gets stuck on a poison pill
  • Classify exceptions: retryable (timeouts, downstream down) vs non-retryable (validation, bad payload; addNotRetryableExceptions(...))
Retry mechanism

Blocking (in-place) retry via BackOff:

@Bean
DefaultErrorHandler errorHandler(KafkaTemplate<Object,Object> t) {
  var recoverer = new DeadLetterPublishingRecoverer(t);
  var backoff = new ExponentialBackOff(1000L, 2.0); // 1s,2s,4s…
  backoff.setMaxElapsedTime(15000L);
  var h = new DefaultErrorHandler(recoverer, backoff);
  h.addNotRetryableExceptions(IllegalArgumentException.class);
  return h;
}

Non-blocking retry with @RetryableTopic: failed messages are forwarded to retry topics (-retry-0, -retry-1…) with delays, so the main partition is not blocked.

@RetryableTopic(attempts = "4",
  backoff = @Backoff(delay = 1000, multiplier = 2))
@KafkaListener(topics = "payments")
void handle(PaymentEvent e) { ... }

@DltHandler
void dlt(PaymentEvent e) { /* alert, store, manual fix */ }

OrderingPreservedLost for retried records
ThroughputPartition stalls during retriesMain flow continues
Use whenOrder matters, short transient errorsLong outages, independent events
Dead Letter Topic (DLT)

A topic where records that exhausted retries (or are non-retryable) are published, so they don't block the pipeline or get lost. Default name: <topic>.DLT (or -dlt with @RetryableTopic) in the same partition number by default.

  • Headers carry original topic/partition/offset and exception stack trace
  • Process via a DLT consumer: alert, persist for analysis, fix and replay to the main topic
  • Monitor DLT volume; it signals bugs or bad upstream data
Interview tip: Pair retries with idempotent consumers, since re-delivery means duplicates are expected. If DLT publish itself fails, the record is retried again, never silently dropped.
